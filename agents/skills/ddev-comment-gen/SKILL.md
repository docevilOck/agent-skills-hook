# DDev Comment Gen — C 项目注释审查与生成

在 ddev-gate 的**代码评审 subagent** 中，与 `ddev-c-pro`（规范 + 质量）、`ddev-clean`（清理项识别，只出清单）同一轮加载，对代码注释做系统性审查和补全，结论与其它维度合并输出。

## 定位

- **触发时机**：ddev-gate 代码评审 subagent 加载（与一致性审查并行；不再要求 c-pro 先通过，也不再有独立注释审查阶段）
- **输入**：代码评审范围内的最终代码（`.c` / `.h`）
- **输出**：`pass` / `blocked`（仅 HIGH 级注释问题触发 blocked）+ 分级清单 + 处置动作（缺口补齐 / 过量删除），并入代码评审合并结论
- **审查范围**：与代码评审范围一致的文件集合

## 审查维度

审查 agent 必须**逐文件、逐函数、逐结构体/枚举**核验，不得仅凭印象判断。

### 1. 文件头注释

- 每个 `.h` 和 `.c` 文件必须包含 `@file` + `@brief` 头注释
- `@brief` 须说明本文件的主要职责，不能仅重复文件名
- `@brief` 只写当前职责，禁止迁移背景、阶段/演进标注（"阶段 N""已迁移""已释放""占位/恢复"）、方案/验证过程等说明，一律进 commit message

```c
/**
 * @file module.h
 * @brief 模块公开 API 定义，提供初始化和数据处理接口
 */
```

### 2. 公开 API 函数注释

每个在 `.h` 中声明的公开函数必须有 Doxygen 注释——它是调用契约的唯一权威位置：

- `@brief`：一句话（≤ 1 行）说明函数做什么
- `@param`：只写签名看不到的信息——约束（可否为 NULL）、单位、取值范围；参数名已自释时不复述类型和含义
- `@return`：返回值含义（无返回值写"无"或"void"）
- `@note` / `@warning` / `@see`：仅在有实质内容时写；**禁止为凑齐标签写空话**

```c
/**
 * @brief  模块初始化，分配并配置硬件资源。
 * @param  cfg  配置参数，不可为 NULL，baud 须 > 0。
 * @return      MODULE_OK (0) 成功，其他为错误码。
 * @note       重复调用前须先 module_deinit。
 */
module_status_t module_init(const module_cfg_t *cfg);
```

### 3. 结构体与枚举注释

- 每个 `struct` / `union` 定义必须有 `@brief` 说明用途
- 成员**默认不写注释**；仅当语义不自释（缩写、裸数值、单位或量纲）或带约束与并发语义时才加 `/**< 说明 */`
- 每个 `enum` 必须有 `@brief` 说明枚举用途
- 枚举值仅在取值含义非直观时加 `/**< 说明 */`；`MODULE_OK` / `ERR_TIMEOUT` 这类自释值不写

```c
/** @brief 模块运行时上下文 */
typedef struct {
    uint32_t baud;
    volatile bool running;  /**< ISR 与主循环共享，仅原子读写 */
    uint8_t rx_buf[256];
} module_t;

/** @brief 模块操作状态码 */
typedef enum {
    MODULE_OK = 0,
    MODULE_ERR_INVALID_ARG,
    MODULE_ERR_TIMEOUT,
} module_status_t;
```

### 4. 私有函数注释

- `static` 函数不强制 Doxygen 格式，但复杂逻辑必须说明意图
- 超过 30 行的 `static` 函数建议添加简要块注释说明职责

### 5. 关键逻辑注释

- 非直观算法、状态机切换、边界条件处理须有少量行内注释
- 注释解释"为什么这样做"，不重复代码本身
- 中断回调、错误恢复路径、硬件 workaround 必须有注释说明
- 能用命名、结构、断言表达清楚的，不补注释；关键逻辑注释是例外，不是默认

### 6. 注释一致性

- 注释内容必须与实际代码行为一致
- 修改函数签名时必须同步更新注释
- 修改函数行为时必须同步更新注释

### 7. 注释语言

- **注释必须使用中文**。本项目注释以中文为准，禁止英文注释（除专用术语、寄存器名、宏名、结构体/函数名等代码标识符外）
- Doxygen 标签（`@brief` / `@param` / `@return` 等）保持英文标签本身，描述内容用中文
- 行内注释 `/**< */` 内容用中文
- 若文件历史中有英文注释，本次改动范围内必须改为中文

### 8. 注释简洁性（Anti-Verbosity）

**默认不写。** 写完代码先自问："删掉这条注释，读者会缺哪一条具体信息？"——答不出具体信息就删除；答得出（为什么这么做 / 约束 / 并发语义 / 单位与取值依据）才保留，且只写这一句。注释补充代码不可见的信息，**不是复述代码本身**；缺失注释与注释过密同为缺陷，双向核验：

- **名可自释不注释**：字段、函数名已充分表达语义时不写，或只写一行；不因"成员都该有注释"的惯例补注释
- **单条注释 ≤ 1 行**：字段、宏、枚举值的行内注释超过 1 行视为冗余（复杂并发协议、硬件 workaround 除外，说明放函数文档）
- **逻辑块注释 ≤ 2 行**：行内 `/* */` 逻辑注释最多 2 行（What + 必要一句 Why）；方案背景、验证过程、替代方案、历史原因等说明写 commit message，不进代码注释；超过 2 行即冗余
- **不复述代码**：注释不得复述可见信息——"锁内提交""跨线程""读取并清零"等若在函数名、lock/unlock 调用、变量名中可见，不写入注释
- **同一语义只写一次**：在唯一权威位置说明（函数文档），调用点 / 字段用指针引用（如"见 ble_request_*()"），不重复展开
- **static 函数不贴 Doxygen**：`static` 辅助函数不强制 `@brief`/`@param`/`@return`；仅复杂逻辑加 2~3 行块注释说明意图
- **调试/追溯标签不进注释**：`[P1_XXX]` 等打点日志标签、迭代追溯标签不得进入注释正文（仓库统一约定除外）
- **背景/演进内容不进注释（全注释类型）**：迁移背景、阶段/演进标注（"阶段 N""已迁移""已释放""占位/恢复"）、方案/实验/验证过程、历史原因等说明一律写 commit message，**任何**代码注释都不得包含——含文件头 `@brief`、常量移除处、字段/成员注释、逻辑块注释。反例：文件头 `@brief` 只写当前职责，不写迁移史；常量移除处不写背景说明（直接删除即可，必要时只写"见 commit XXXX"）
- **冗余判据**：逐处列清单（文件:行号 + 类型 + 删除理由），**处置动作一律是删除**，不靠改写、扩写或补注释消解；冗余不阻塞放行（见「问题分级」）

### 9. 计划与文档术语泄漏

注释只描述**代码自身的事实与约束**，不得携带设计/计划文档的叙述结构。以下术语出现在代码注释中即为缺陷（**出现即 `blocked`**，须改写为代码语境）：

- 步骤/阶段编号：`step 1` / `step 2` / `第一步` / `阶段 N`
- 文档定位符：`§X` / `spec §X` / 章节号 / `见 spec/xxx.md`
- 计划与任务编号：`T1` / `Task N` / 计划文件名（`docs/plans/...`）
- 变更叙述：`本轮` / `本次` / `新增` / `迁移` / `改造后` / `已改为`（叙述「这次改了什么」而非「代码是什么」）
- 迭代/评审语汇：`迭代 N` / `评审发现` / `方案 A` / `验证通过`

**改写方式**：把文档话翻成代码话——`step 1 抽干队列` → `先抽干输入队列`；`下游` → 具体函数名；`本轮新增` → 直接删除。

**机械检查**（对本次改动的新增行执行）：

```bash
git diff | grep -E '^\+.*(step|§|阶段|本轮|本次|新增|迁移|计划|T[0-9]|spec)'
```

**豁免**：函数名、宏名、结构体名、文件名等代码标识符中本身含上述词的不计。

## 注释规范

- 默认不写注释；确需写时用简洁中文描述"做了什么 + 为什么/约束"，**宁缺毋滥**：名可自释者不注释，同一语义只写一次（判定方法见维度 8）
- 注释只描述代码自身的事实与约束，不携带设计/计划文档的术语与步骤编号（见维度 9）
- 使用项目统一的 Doxygen 风格（`/** */` 或 `///`）
- 常用 Doxygen 标签：`@brief` / `@param` / `@return` / `@note` / `@warning` / `@see` / `@todo` / `@retval`

## 问题分级（与 `ddev-gate` 共用口径）

**分流原则：客观项可阻塞，裁量项只列清单。** 判定注释缺陷时先定级，再决定是否 `blocked`。

| 级别 | 情形 | 判定 |
|------|------|------|
| HIGH | 文件头 `@file` + `@brief` 缺失（维度 1）；`.h` 中声明的公开函数 Doxygen 缺失（维度 2）；公开 `struct` / `enum` 的 `@brief` 缺失（维度 3）；**注释与代码行为矛盾**（维度 6）；计划/文档术语泄漏（维度 9） | `blocked` |
| MEDIUM | 结构体 / 枚举**成员**行内注释缺失（维度 3）；`static` 复杂函数缺少意图说明（维度 4）；本次改动范围内注释仍为英文（维度 7） | 列清单，不阻塞；主 agent 同轮补齐 |
| LOW | 局部逻辑 / 行内注释缺失（维度 5）；注释冗余——复述代码、单条超长、逻辑块超 2 行、`static` 贴 Doxygen、调试标签（维度 8） | 列清单；**冗余项同轮删除**，不阻塞 |

判据说明：

- **错误注释 > 缺失注释**：注释与行为矛盾会让读者按错误理解改代码（HIGH）；单纯缺注释只是信息不足
- 维度 3 的成员注释按「语义不自释 / 带约束才写」判定，属裁量，故成员注释缺失为 MEDIUM 而非 HIGH
- 维度 8 的冗余项**不按累计数量阻塞**，统一列为 LOW，但**必须在同轮删除**：注释过量是缺陷，删掉即修好，不存在"补齐"一说
- 维度 9 的术语泄漏有确定性 grep 判据，保持 HIGH
- MEDIUM / LOW 不阻塞放行，但主 agent 仍须同轮补齐；结论中要标明哪些已补、哪些留作遗留

## 审查流程

1. 遍历所有目标 `.h` 文件，逐一检查文件头、公开函数、结构体、枚举的注释必要性与缺口（默认不写，见维度 8）
2. 遍历所有目标 `.c` 文件，逐一检查文件头、私有函数的注释必要性与缺口
3. 检查关键逻辑（中断 ISR、错误恢复、状态机、复杂算法）的注释覆盖
4. 检查注释语言是否使用中文（专有术语、标识符除外）
5. 检查注释简洁性（维度 8）：名可自释却硬补注释、单条超 1 行、逻辑块注释超 2 行、复述代码、static 贴 Doxygen、调试标签进注释，以及文件头 `@brief`/常量移除处/字段成员处的迁移背景与阶段/演进标注（"阶段 N""已迁移""已释放""占位/恢复"）和方案/验证过程说明等
6. 检查计划与文档术语泄漏（维度 9）：`step N` / `§` / 阶段编号 / `本轮` / 计划文件名等；对本次改动的新增行执行维度 9 的 grep 命令
7. 缺失项与冗余项分别记录（文件:行号 + 类型 + 描述 + 处理建议文本）
8. 按「问题分级」定级后出结论：**存在 HIGH 级 → `blocked`** + 附清单；只有 MEDIUM / LOW 级 → `pass`，同时附分级清单并标注哪些已同轮补齐、哪些留作遗留

## 审查结论格式

```
ddev-comment-gen 审查结论：[pass | blocked]

问题分级汇总：HIGH N 条 / MEDIUM N 条 / LOW N 条

清单（每项标注级别与处置动作：缺口=补齐，冗余=删除；HIGH 项同时是阻塞项）：
- module.h:42 — [缺失] module_init 缺少 @param cfg 注释
- module.c:10 — [缺失] 缺少 @file 头注释
- module.h:25 — [缺失] module_cfg_t 结构体缺少 @brief，成员 baud 缺少行内注释
- module.c:88 — [缺失] ISR 回调缺少说明注释
- module.c:60 — [冗余] 字段注释 3 行复述锁逻辑，字段名已自释，压到 ≤1 行
- module.c:120 — [冗余] static 辅助函数贴完整 Doxygen，应降为 2~3 行块注释
- module.c:88 — [冗余] 逻辑块注释 5 行含方案背景与验证过程，压到 ≤2 行，背景进 commit message
- prt_z5_cfg.h:432 — [冗余] 常量移除处写"补光灯控制权已迁移小核"迁移背景，应删除该注释，背景进 commit message
- prt_light.c:1 — [冗余] 文件头 @brief 含"阶段 2：torch 恢复真实下发""控制权已迁移"演进标注，@brief 只保留当前职责，迁移史进 commit message
- prt_screen.c:468 — [术语泄漏] 注释含 "step 1 … step 2 …"（设计文档的步骤编号），改写为代码行为描述
```

## 审查模式

当本 skill 被 ddev-gate 的代码评审 subagent 加载时，必须使用 `reviewer-prompt.md` 作为任务模板执行审查。该模板定义了审查输入、审查维度优先级和输出格式；审查结论并入代码评审合并结论。

## 进度记录

审查完成后将结果写入项目根目录的 `progress.md`：

- 通过：记录"comment-gen 审查通过"，附检查项通过数/总项数
- 阻塞：记录"comment-gen 审查发现 N 个 HIGH 级阻塞项"，逐项列出文件:行号 + 问题描述；同轮另附未补的 MEDIUM / LOW 遗留项
- 追加时间戳和审查结论到最近一次执行日志后
