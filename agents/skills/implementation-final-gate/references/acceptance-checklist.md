# 实现最终验收检查清单

这个清单用于 `implementation-final-gate` 的详细对照。

默认规则：design 文档只声明“这次要做什么”。凡是 architecture、detail、exec plan 中没有明确写到的实现内容，默认按未批准处理，不要求文档再额外列一份“明确不做”清单。

## 1. 输入完整性

- 是否已经定位本次改动对应的 architecture 文档
- 是否已经定位本次改动对应的 detail 文档
- 是否已经定位本次改动对应的 exec plan
- 是否已经定位实际代码改动范围
- 是否拿到了必要的验证证据

缺任何关键项，都不能直接给 `pass`。

如果 architecture / detail / 代码范围三者之一无法唯一定位，应停止一致性验收，不要退化成泛化 review。

## 2. 架构一致性

- 模块职责是否与 architecture 文档一致
- 模块边界是否与架构图一致
- 接入点是否与设计说明一致
- 调用方向和依赖关系是否与设计一致
- 是否新增了架构文档未提及的跨模块耦合

## 3. 结构体与状态一致性

- 结构体定义是否与 detail 文档一致
- 字段归属是否一致
- 配置、运行时状态、输入、输出是否按文档拆分
- 运行时状态是否收敛到上下文对象
- 是否出现文档未批准的共享可变状态

## 4. 数据流与流程一致性

- 主流程是否与 detail 文档或流程图一致
- 数据流入口、转换、出口是否一致
- 状态迁移是否一致
- 错误路径是否一致
- 是否新增文档未说明的旁路逻辑
- exec plan 要求的关键实现步骤是否真的落地
- 是否出现计划里明确要求、但代码里漏做的环节

## 5. C 结构纪律

- 是否新增业务全局变量
- 是否出现长链 `if/else`
- 是否用魔法数字表示状态
- 是否把多类职责塞进单函数
- 是否违反文档约定的 `switch` / 表驱动 / 状态机方案
- 是否破坏 `static` 私有边界

## 6. 偏离判断

如果实现与文档不一致，必须明确归类：

- 文档过时，实现合理
- 实现偏离设计，需要修代码
- 实现偏离 exec plan，需要修代码
- 设计本身不完整，需要补文档
- 当前证据不足，不能判断

不要把所有差异都归类成“小问题”。

## 7. 验证证据

- 构建是否通过
- 静态检查是否通过
- 测试是否覆盖关键路径
- 人工验证是否覆盖硬件或现场行为
- 证据是否真的对应本次结论
- 这些证据是否是本轮新的有效证据，而不是历史残留结果

如果结论依赖人工确认但没有人工证据，只能降级。

如果没有本轮新的有效证据，不能给 `pass`。

## 8. 输出约束

最终必须明确：

- 结论是 `pass`、`need-info` 还是 `blocked`
- 差异归类是什么
- 哪些点已确认一致
- 哪些点不一致
- 哪些风险未覆盖
- 是否需要回到 architecture/detail 文档更新
- 如果不一致，是否已经明确列出打回主 agent 的修改项

## 9. `need-info` 与 `blocked` 分流

- 缺信息但补齐后还能继续验收：`need-info`
- 基线冲突、关键文档缺失、实现偏离设计/计划，或前提不成立，导致继续验收没有意义：`blocked`

不要把所有“不够确定”都打成 `need-info`。
