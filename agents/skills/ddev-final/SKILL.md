# ddev-final — 最终设计归档

记录经过实机调试后的最终实现设计，补全 spec/plan 与实际代码之间的差异。

**开始时声明：** "正在使用 ddev-final skill 归档最终设计。"

## 何时使用

- 实现 + 调试完成，代码已提交
- 最终设计与原 spec/plan 存在差异（调试中修改了方案）
- 需要给后续维护者留下一份"实际长什么样"的设计文档
- 准备关闭 feature 分支或进入发布前

不使用的情况：
- spec/plan 还没写 → 先用 ddev-spec / ddev-plan
- 还没调试完 → 先调完再说
- 实现与原计划完全一致且无 bug → 在 progress.md 标注即可，不需要 final 文档

## 文档位置

```
docs/plans/YY-MM-DD_name/final/final_design.md
```

如果在已有计划目录下：直接创建 `final/` 子目录。

## 图怎么画

### ⚠️ 硬门禁：画图前必须先加载 ddev-diagram

**在任何 ASCII 图动笔之前，必须执行 `Skill("ddev-diagram")` 加载绘制规范。加载完成前禁止写任何 ASCII 图。**

规范要点：Unicode 制表符、正交连线、英文框内标签、一图一事。

优先画：
1. 架构总览（模块框 + 调用关系）
2. 核心流程图（如两阶段处理、多文件下载时序）
3. 函数调用关系（拆分后）

不需要画：
- 原始 spec 里已正确且未变化的部分（引原文档即可）
- 流程图不需要画到每行代码的粒度

## 内容要点

### 差异表（必填）

原计划 vs 最终实现，**每项必须写原因**。没有差异就写"无"。

### 调试 bug 记录

只记**实现阶段发现的 bug**，不记 spec/plan 阶段就发现的设计问题。
对每个 bug 记录：症状（日志/现象）、根因（代码位置）、修复方法。
可选：附实机日志片段或二进制验证数据。

### 函数结构

如果代码经过了重构（如拆函数），画出拆分后的函数调用关系。
标注每个函数的大致行数和职责。

### 数据结构

标注最终状态的关键结构体字段、新增枚举值、状态迁移。
对于嵌入式 C：注明 buffer 所有权、谁分配谁释放、大数组放哪。

## 写法原则

- 简洁优先：文档是给未来维护者看的，不是给当前调试过程写日记
- 图优先：能用图说清的不用长文
- 只写"最终状态"，不写"调试过程中试过 A 不行换 B 最后选了 C"
- 原 spec 里正确且不变的部分：一句话引原文档，不重复写

## 与其他 skill 的关系

- 上游：`ddev-exec`（实现）+ 实机调试
- 并行：`ddev-diagram`（画图规范）
- 下游：`neat-freak`（归档清理时可能会引用 final 文档）
- 替代：原 spec 文档被本 final 文档**补充**而非替换——spec 保留作为设计意图记录，final 记录实际落地结果

## 自检

文档完成后逐项核对：

1. 差异表是否覆盖了所有与原计划不同的地方？
2. 架构图是否反映实际函数调用关系？
3. 每个 debug bug 是否有症状/根因/修复三要素？
4. ASCII 图是否通过 ddev-diagram 门禁（右边框对齐、等宽、无斜线、T 型完整、无断线）？
5. 函数行数是否标注（≤80 行的证据）？
6. 数据结构注释是否与 `.h` 中的实际定义一致？
