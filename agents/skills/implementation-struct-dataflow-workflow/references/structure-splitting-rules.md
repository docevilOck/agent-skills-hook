# 结构体拆分规则

## 先做什么

先从已确认的架构文档里，找出本次改动真正会影响的结构体，不要把所有历史结构体都拉进来。

同时把这些内容一起看：

- 相关状态枚举
- 关键缓冲区或协议帧
- 谁拥有这份状态，谁跨调用保留它

## 分类方式

- 新增：这次第一次出现
- 修改：已有结构体字段、语义或职责发生变化
- 复用：本次仍然使用，但不需要改定义
- 废弃候选：理论上可被替代或收敛，但本轮不直接删除

## 拆分原则

- 一个结构体只归一个主职责
- 结构体过多时，按模块或流程拆成多个文档
- 文档要能看出结构体之间的依赖和流向
- 配置、运行时状态、缓冲区、输入载荷、输出结果尽量分开建模
- 需要长期保存的状态优先挂到 `context` / session / handle，而不是散在全局变量
- 一个结构体如果既负责配置、又负责流程状态、又负责暂存输入输出，通常已经该拆

## 判断标准

如果一个结构体说明里需要写很多“顺便”、“另外”、“也可能”，通常说明它职责已经太散，应该拆开。

如果一个字段无法明确回答“谁写、谁读、何时失效”，通常说明它要么放错地方，要么缺生命周期设计。
