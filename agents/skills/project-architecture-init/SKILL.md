# 项目架构规范初始化

## 定位

这是**项目级架构规范契约**，不只是代码说明或代码导航。目标是让 AI（和人）在修改代码前知道：模块职责是什么、边界在哪里、哪些依赖允许、哪些改动会破坏架构。

- 每个模块独立成文，模块文档必须讲清楚：**模块负责什么、不能负责什么、允许依赖谁、对外暴露什么**
- `仓库目录映射` 仍然必须准确，但它服务于架构约束：帮助 AI 把改动限制在正确模块内
- 文档要能回答”这次代码改动是否越界”，而不是只回答”代码在哪里”

## 双受众设计：约束薄、学习厚、物理分离

产出的架构文档同时服务两类读者，但**物理分离**以避免 token 浪费：

- **AI 修改代码前**：只读约束文件（`_概览.md` 或单文件模块的分隔线以上部分），约 30-50 行，不吞学习内容
- **新人上手**：先读总览的”系统如何工作”和”概念词汇表”，再按推荐顺序读各模块的学习文件（关键流程、数据结构、设计决策）

对于大模块，约束和学习分文件存放，各取所需、互不干扰。

## 与实现架构的区别

- **本 skill**：初始化项目级长期架构规范，产出稳定的模块边界、依赖规则和变更门禁。它约束后续所有代码修改。
- **`implementation-architecture-workflow`**：针对某一次代码改动，编写临时实现架构文档。它必须读取并遵守本 skill 产出的项目级架构规范。

## 探索要求

1. 先并行分发多个子代理，从目录结构、构建目标、入口调用链、公共接口和数据所有权等视角探索仓库，收集模块边界候选。
2. 再根据识别出的功能模块，并行分发多个子代理分别深入探索各模块，补齐职责、边界、对外接口、依赖方向、状态所有权和关键数据结构。
3. 汇总所有子代理结果后，再统一写架构总览、模块规范文档和 `AGENTS.md`，不要在探索完成前提前定稿。
4. 额外分发一个"新人视角"子代理，专门识别：
   - 项目中需要解释的领域术语、缩写和特有概念
   - 真正的代码入口点和启动流程
   - 1-2 个最适合做端到端走读的典型业务场景（覆盖最多模块的那个流程）
   - 代码命名约定和惯用模式（错误处理、内存管理、日志风格等）
5. 根据模块大小判定文档形式（见"模块边界识别"第8条），大模块用子目录、小模块用单文件

## 触发条件

- 新项目启动，需要建立长期架构规范
- 现有项目缺少架构约束文档，需要补建
- 用户明确要求"写架构文档"且不是针对某次代码改动
- 用户希望约束 AI 后续改代码范围，避免破坏既有架构

## 基本流程

1. 按"探索要求"探索仓库，形成模块候选、职责候选和依赖候选
2. 写架构总览 `01_架构总览.md`，按"架构总览模板"编写
3. 为每个模块写独立规范文档，放入 `modules/` 目录，按"模块规范模板"编写
4. 需要图示时，按 diagram-workflow 规范手写 ASCII 到 `.md`，图附近标注用途说明
5. 创建或更新仓库根目录的 `AGENTS.md`（以及 `CLAUDE.md` 若存在），写入架构规范读取和变更门禁规则（见下方"AGENTS.md 规则注入"）
6. 全部完成后做验收检查（见"验收标准"）

## 模块边界识别

按以下优先级判定模块边界：

1. **公开接口边界**：头文件、导出类、路由、命令、服务接口、包入口等对外暴露面，优先作为模块边界依据
2. **目录即模块**：如果仓库已经按目录划分了子系统/组件，直接以目录为模块单位
3. **数据所有权**：谁拥有关键状态、配置、缓存、设备句柄、数据库表或领域对象，谁就是对应职责的主模块
4. **入口文件回溯**：找 `main()`、`app init`、注册函数等入口，反向追踪调用链来聚合文件
5. **独立构建目标**：如果某目录有独立的 `CMakeLists.txt`、`Makefile`、`Cargo.toml` 等，就是一个模块
6. **平铺文件兜底**：如果几十个文件平铺在一个目录里，按功能前缀分组（如 `uart_*.c`、`spi_*.c`），每组为一个模块
7. **嵌套处理**：模块内若有明显的子模块边界（如 `module/sub_a/`、`module/sub_b/`），子模块独立成文，编号用两级序号（如 `02-01_子模块名.md`）
8. **模块大小判定**：满足以下任一条件即为"大模块"，使用子目录模板；否则为"小模块"，使用单文件模板：
   - 源码文件超过 10 个
   - 有明显子模块边界（含独立子目录）
   - 关键流程超过 3 个独立分支
   - 关键数据结构超过 5 个
   - 涉及多个独立设计决策

不确定边界时，宁可先拆小并写明"边界待确认"，不要把多个职责合成一个大模块。

## 文档目录规划

小模块用单文件，大模块用子目录。AI 只读 `_概览.md`（或单文件分隔线以上），新人按需读学习文件。

```
docs/architecture/
├── 01_架构总览.md                # 薄：含项目简介、概念词汇表、阅读顺序、端到端走读链接、架构原则、依赖规则、常见任务地图
├── modules/
│   ├── 02_<简单模块>.md           # 小模块：单文件，约束在前（分隔线以上），学习内容在后
│   ├── 03_<大模块>/               # 大模块：建子目录，约束与学习物理分离
│   │   ├── _概览.md                # 极简约束（30-50行）：职责+边界+接口+依赖+状态所有权+修改范围+检查清单
│   │   ├── 关键流程.md             # 厚：流程图+步骤说明
│   │   ├── 主要数据结构.md         # 厚：结构体定义+设计意图+生命周期
│   │   ├── 设计决策.md             # 厚：关键取舍与理由
│   │   └── 常见修改场景.md         # 正向任务地图
│   └── 04_<另一大模块>/
│       ├── _概览.md
│       ├── 子模块A/               # 大模块内的子模块边界
│       │   ├── _概览.md
│       │   └── 关键流程.md
│       └── ...
└── diagrams/                      # 架构图文件（手写 ASCII 到 .md）
    └── *.md
```

## AGENTS.md 规则注入

所有架构文档生成后，在仓库根目录创建或更新 `AGENTS.md`，写入以下内容（按实际模块名和路径调整）。如果仓库根目录已有 `CLAUDE.md`，则同步更新 `CLAUDE.md`，将同样的架构规范段落追加或更新到其中。

```markdown
<!-- AGENTS.md — 由 project-architecture-init 自动生成 -->

## 项目架构规范

本仓库已建立项目级架构规范，位于 `docs/architecture/`。

### 修改代码前

- 先读 `docs/architecture/01_架构总览.md` 的"依赖规则"和"架构变更门禁"
- 大模块：只读 `docs/architecture/modules/0X_<模块名>/_概览.md`
- 小模块：只读 `docs/architecture/modules/0X_<模块名>.md` 分隔线以上的约束部分
- 不要读 `关键流程.md`、`主要数据结构.md`、`设计决策.md`、`常见修改场景.md`，除非需要理解代码行为才能正确修改
- 修改必须优先落在模块约束标注的"允许修改范围"内，不要因为路径相近就跨模块改代码
- 如果实现需要突破模块边界、增加反向依赖、移动文件、改变公共接口或迁移状态所有权，必须先更新架构文档，再改代码

### 架构变更门禁

以下变化视为架构变更，不能只改代码：

- 新增、删除、合并或拆分模块
- 改变模块职责或数据所有权
- 新增跨模块依赖，尤其是反向依赖、循环依赖或下层依赖上层
- 修改公共接口、协议、持久化格式、构建产物或外部可见行为
- 将原本私有的状态、函数或文件提升为跨模块共享
```

如果 `AGENTS.md` 已存在，检查是否已有架构规范相关段落，有则更新内容，无则追加在合适位置。

## 图怎么画

图画法统一遵循 [diagram-workflow](../diagram-workflow/SKILL.md) 规范。所有图直接手写 ASCII 到 `.md`，不经过 PlantUML。

优先画：

- 系统边界图（组件图）：看清系统与外部的关系
- 模块依赖图（组件图）：看清允许依赖方向和禁止方向
- 状态所有权图：看清关键状态属于哪个模块
- 核心数据流图（活动图/时序图）：看清主要数据处理路径

画图步骤：

1. 按 diagram-workflow 选图策略确定图型
2. 手写 ASCII 图到对应 `.md` 文档
3. 在图上方标注用途说明

## 验收标准

初始化完成后，逐项检查：

| 检查项 | 标准 |
|--------|------|
| 模块覆盖 | 所有可识别模块都有对应文档，无遗漏 |
| 大小判定 | 每个模块正确判定为小模块（单文件）或大模块（子目录） |
| 约束分离 | 大模块有 `_概览.md`，小模块约束在分隔线以上；AI只读约束约30-50行 |
| 职责边界 | 每个模块约束文件都写清"负责"和"不负责" |
| 依赖约束 | 总览和模块约束文件都写清允许依赖与禁止依赖 |
| 状态所有权 | 关键状态、配置、缓存、句柄都有明确归属 |
| 修改门禁 | 每个模块约束文件都有"允许修改范围"和"修改前检查清单" |
| 路径可定位 | 每个模块的"仓库目录映射"指向真实存在的目录/文件 |
| 图完整 | 架构总览有模块依赖图，大模块 `关键流程.md` 有流程图 |
| 交叉引用正确 | 模块间依赖关系在文档中有标注且路径正确 |
| 一致命名 | 模块名、文档名、图中标签三者一致 |
| AGENTS.md+CLAUDE.md | 仓库根 `AGENTS.md`（及 `CLAUDE.md` 若存在）含架构规范索引和变更门禁 |
| 概念词汇表 | 架构总览包含核心概念词汇表 |
| 阅读顺序 | 架构总览包含推荐阅读顺序 |
| 端到端走读 | 产出独立的 `端到端场景走读.md`，至少 1 个跨模块场景 |
| 学习内容 | 大模块有 `关键流程.md`/`主要数据结构.md`/`设计决策.md`/`常见修改场景.md`；小模块分隔线以下有对应内容 |
| 常见任务 | 架构总览有常见任务地图 |

## 文档维护

架构规范不是一次性的。以下情况必须更新：

- 新增/删除/合并/拆分模块时，更新 `01_架构总览.md` 模块列表，新增/删除对应模块文档（或目录），同步更新 `AGENTS.md`（及 `CLAUDE.md` 若存在）的文档索引
- 模块文件迁移时，更新对应模块约束文件（`_概览.md` 或单文件分隔线以上）的"仓库目录映射"
- 模块职责发生变化时，更新约束文件的"模块职责"和"职责边界"
- 新增跨模块依赖时，更新总览的"依赖规则"和相关模块约束文件的"允许依赖"
- 状态、配置、缓存、句柄或关键数据结构所有权变化时，更新约束文件的"状态与数据所有权"
- 修改公共接口、协议、持久化格式或外部行为时，更新约束文件的"对外接口"和"允许修改范围"
- 代码行为变化时，同步更新对应学习文件（`关键流程.md`、`主要数据结构.md`、`设计决策.md`、`常见修改场景.md`），保持与代码实际行为一致
- 端到端走读和常见任务地图在涉及流程变化时同步更新

维护时优先保证约束文件准确（`_概览.md` 或单文件分隔线以上），这是 AI 做门禁检查的唯一入口。学习文件次之，但过期信息对新人的伤害比没有信息更大——如果不能及时更新，宁可删除对应学习文件也不保留过时内容。

## 完成后

架构规范初始化完成后，不必自动进入实现工作流。仅在用户后续发起具体代码改动时，才按需要触发 `implementation-architecture-workflow`，并让该实现文档显式遵守 `docs/architecture/` 中的项目级约束。
