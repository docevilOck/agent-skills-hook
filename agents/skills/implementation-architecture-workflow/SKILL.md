# 实现架构工作流

## 作用

在进行代码修改（新增、重构、修复）前，先编写实现架构文档，理清改动边界和模块关系，再进入编码。本 skill 仅用于**代码改动场景**，项目的整体架构文档初始化请使用 `project-architecture-init`。

图怎么画、怎么命名、怎么渲染、怎么同步维护，统一遵循 [diagram-workflow](../diagram-workflow/SKILL.md)。

架构文档默认落到 `docs/plans/YY-MM-DD_name/architecture/<feature-name>.puml` 和 `docs/plans/YY-MM-DD_name/architecture/<feature-name>.md`。

默认优先用于嵌入式 C / 纯 C / Rust / HTML 的改动，尤其是 BSP、驱动、协议、板级初始化和静态页面这类需要看边界的工作。

## 联动顺序

1. 先用这个 skill 把架构文档写出来或改完。
2. 再交给 `diagram-workflow`，把同一份架构文档细化成图，并决定哪些图可以自动 ASCII，哪些图必须手写 ASCII。
3. 架构文档和图都确认后，再进入 `writing-plans`，把已确认的设计拆成执行计划。

## 基本流程

1. 先判断这次改动属于哪一类：
   - 现有代码修改
   - 从零搭建新系统
   - 新增独立功能模块
2. 先写架构文档里的图和说明。
3. 按 `diagram-workflow` 决定展示图策略：复杂图默认手写 ASCII，简单图才可参考自动 ASCII 渲染。
4. 检查架构文档是否清楚、是否过挤、是否容易比较。
5. 在每张 ASCII 图附近标注对应 `.puml` 源路径。
6. 如果看不清，先判断是否该改成手工 ASCII，而不是默认重新渲染。

## 输出边界

该 skill 产出的实现架构文档是设计说明，不是对话纪要、答疑记录或方案说服稿。

文档中禁止写入以下内容：

- 复述用户在对话里的疑问、担心、追问、争论过程
- 带说服语气的章节，例如“为什么现在值得先写设计文档”“为什么不是小改动”“为什么不直接改”
- 过程性结论或路线推荐，例如“建议路线”“当前结论”“推荐方案”
- 面向当前对话上下文的问答整理，而不是面向代码实现的设计信息

文档只保留实现直接需要的信息：目标与范围、接入点、模块边界、主流程、前后对比、约束、风险、验证要点。

## 固定结构

实现架构文档默认只包含以下章节，除非用户明确要求，否则不要新增额外章节：

1. 目标与范围
2. 架构总览
3. 现有代码接入点
4. 核心流程
5. 修改前后对照
6. 约束与风险
7. 验证要点

## 图怎么选

- 架构规划：画组件图、边界图，先看模块关系和职责边界
- 接入点：画编号接入点图，先看改动从哪里接入
- 功能流程：画流程图或活动图，先看主路径和关键分支
- 修改对比：画 before / after 对照图，先看前后变化

如果不确定，优先选“架构规划”，再补接入点和流程图。

## 最低验收

在实现开始前，文档至少要讲清楚：

- 这次改什么
- 接到现有代码的哪里
- 主流程怎么走
- 修改前后差了什么
- 每张 ASCII 图对应的 `.puml` 源文件在哪

## 生成后自检

如果文档中出现以下标题或同类表达，视为不合格，必须删除或改写：

- 为什么……
- 建议路线
- 当前结论
- 是否值得……
- 这是不是小改动
- 用户疑问
- 问答
- 决策过程
