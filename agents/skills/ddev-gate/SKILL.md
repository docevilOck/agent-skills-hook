# 实现最终验收门禁

## 作用

这个 skill 用于代码实现阶段的最终验收。

它只审两类判断；对**大改动**，同一轮**同时派发两个独立 subagent**：

- **一致性审查（A）**：只核对代码实现与 spec / detail / `docs/architecture/` 文档规划的**架构**是否一致——模块边界与职责归属、接口位置与签名、调用与依赖方向、状态所有权、数据流与关键流程骨架、联动注册点。只承担 V1（越界 / 漏改）、V2（三方口径矛盾）、V5（注册点齐备），不做逐行细节对照，不做命名、风格、注释、代码质量判断。
- **行为评审（B）**：只报会改变行为的缺陷（崩溃 / 边界 / OOM / 返回值 / 并发 / 资源释放 / 未实现 / 安全），并做 V3 假修复对账。注释只报**与代码行为矛盾**的项；清理清单只在终轮出一次。C 项目加载 `ddev-c-pro`（质量参考）+ `ddev-comment-gen`（语义段）+ `ddev-clean`（终轮清单）；非 C 项目加载 `ddev-code-review` + 对应语言 skill（如有）。

**能用脚本判定的全部前置到机械闸**（注释机械项、卫生项、范围对账、注册点、证据新鲜度、文档基线），不进审查对话。

两个 subagent 在同一轮并行派发。复审是**增量**的：只审本轮 diff + 上一轮未闭环项，不重扫全仓。收敛条件仍是**两个审查在同一份最终代码上都 `pass`，且该轮没有任何代码修改**，但受轮次预算约束（默认 3 轮，见「核心流程」步骤 7）；超出预算输出 `need-info` + 遗留清单，交用户裁决。

流程分三段闸：

1. **机械闸（P0）**：主 agent 跑确定性检查（范围对账、注释机械项、卫生项、注册点清单），不派 subagent。有 FAIL 先修。
2. **语义闸（P1）**：只审五类高价值判断（V1~V5，见「价值矩阵」）。能用脚本判定的项不再进审查对话。
3. **收口闸（P2）**：增量复审 + 影响面兜底 + 累计漂移对账（见「复审兜底」）。

一致性审查发现的架构偏离按「修正优先、记录兜底」处理：

- 能修正的，修正到与文档规划一致；
- 无法修正，或经过考虑决定不修正的，写入 `implementation-notes.md` 的 Deviations（偏离点、理由、影响范围），审查确认已记录后可通过；
- 既未修正、也未记录的偏离 → `blocked`。

**小改动（默认）** 走 compact 路线：先过机械闸，再拉 1 个独立 subagent 一次性完成五类语义审查，输出一份结论，不派发第二个 subagent。

> **与旧流程的区别**：① 新增机械闸（P0），注释机械项与卫生项不再逐条写进报告；② 代码评审从"规范+质量+注释+清理四合一"收敛为"行为优先 + 机械闸解读"；③ 复审从"任何修改都全量重跑"改为"增量 + 影响面兜底 + 漂移对账"；④ 轮次从无上限改为 3 轮预算；⑤ 结论必须带机读头。

## 何时使用

在以下场景使用：

- 一个实现任务完成后，需要做正式验收
- 准备声称“已经完成实现”或“已经满足设计”
- 准备把改动交给下游联调、测试、提交或发布
- 需要确认代码实现没有背离 spec / detail 文档规划的架构

如果只是想先检查有没有跑验证命令，优先用 `verification-before-completion`。

如果只是想让另一个视角找 bug，优先用 `ddev-code-review`。

如果主 agent 正准备宣称“已经完成计划”“已经按计划实现完成”“可以正式收尾”，这个 skill 是必经门禁。

## 输入要求

开始验收前，至少定位这些输入：

- **`gate-scope.yaml`**（改动面清单，由 `ddev-plan` / `ddev-exec` 产出；格式见 [references/gate-scope.md](references/gate-scope.md)）
- 本次改动对应的 spec 文档路径
- 本次改动对应的 detail 文档路径（含 structures / dataflow / flows）
- 相关代码变更范围
- 本轮验证证据

能拿到的话，额外读取：

- `implementation-notes.md`（由 ddev-exec 在执行过程中写入，含 Design Decisions / Deviations / Tradeoffs / Open Questions）
- `task_plan.md`（由 ddev-exec 创建，含任务 checkbox 和 Errors 表）
- 结构图 / 流程图 / 数据流图
- `ddev-plan` 产出的执行计划（只用于确定范围和任务背景，不作为架构真源）
- 构建、测试、静态检查或人工验证结果

如果连 spec 或 detail 文档都没有，不能直接给通过结论。

如果无法唯一定位 spec 文档、detail 文档或本次改动范围，不要退化成泛化 code review。此时应立即停止验收，并输出：

- `need-info`：信息暂时不足，但理论上可补齐
- `blocked`：当前上下文下无法继续定位或缺失关键设计输入

执行计划只用于确定范围和理解任务背景；一致性审查不再要求 exec plan 的每个步骤都落地，也不再把 exec plan 当作独立设计真源。

## 改动面清单（`gate-scope.yaml`，机械闸的输入契约）

范围不再靠"从 diff 反推"，而由 `ddev-plan` / `ddev-exec` 产出的**改动面清单**给定。文件放在计划目录下（与 `exec_plans/` 同级），格式见 [references/gate-scope.md](references/gate-scope.md)。

要点：

- `planned_files`：计划内的 modify / create / delete 三张清单，机械闸用它判「越界」与「漏改」
- `impact_surface`：已知受影响符号、调用方、公共头文件（供 P2 影响面兜底对账）
- `registration_points`：必须同步登记的联动点（枚举、分发表、回调表、构建开关）
- `verification`：验证命令与证据文件，及其最近运行时间
- `baseline`：首轮审查时的代码锚点，用于累计漂移
- `deviations`：执行期偏离，每条带 `DEV-ID`

清单缺失时：streaming 路线判 `need-info`（要求补清单，或由主 agent 从 spec / detail 手工整理后落盘）；compact 路线允许由 diff 推导，但必须标 `SCOPE: derived`，且推导范围不得作为最终 `pass` 的唯一依据。

## 机械闸（P0，必须，不派 subagent）

目的：把所有能用确定性命令判定的事情干完，避免用 5KB 报告讨论 `@brief` 缺没缺。

主 agent 按 [references/mech-checks.md](references/mech-checks.md) 跑 6 组检查，压缩成一张表：

| 组 | 检查 | 判据 |
|---|---|---|
| M1 | 范围对账 | `git diff --name-only` + `git status --porcelain` vs `gate-scope.yaml` 的 planned_files / allowed_globs |
| M2 | 注释机械项 | 文件头 `@file`/`@brief`、英文注释、术语泄漏、`#if 0`、注释掉代码、定义处冗余 `extern` |
| M3 | 卫生项 | 裸 `printf`/`fprintf`、魔术数字、过长函数（>80 行）、零引用符号 |
| M4 | 注册点 | `registration_points` 逐项在目标文件中命中 |
| M5 | 证据 | `verification.evidence` 存在且 mtime 晚于最后一次代码修改 |
| M6 | 文档基线 | spec / detail / `docs/architecture/` 在 gate 期间是否被改动 |

处理规则：

- M1 / M4 / M5 / M6 有 FAIL：主 agent 先修或补齐，**不派 subagent**
- M2 / M3 有命中：允许派发，命中项只作为 P1 的**输入**，不在审查报告里逐条论述
- M6 有改动：视为设计基线变更，必须显式声明并重跑 A 全量（见「累计漂移控制」）
- 机械闸结果压缩为「机械闸摘要」随最终输出附上，不占正文

## 价值矩阵（P1 只审这五类）

只有"脚本最多给线索、结论必须读文档+读代码+交叉对账"的判断才进 P1。

| 编号 | 价值点 | 判据要点 | 必须给的证据 |
|---|---|---|---|
| V1 | 越界与漏改 | 实际改动 vs 声明文件表；新增文件/构建脚本/注册表是否在计划内 | 越界清单 + 漏改清单，附 `git diff --name-only` 对账 |
| V2 | 三方口径矛盾 | spec / detail / 代码 / 注释 是否互斥；发现矛盾必须给**定稿建议**（唯一口径 + 改哪份文档） | 矛盾对 + 建议口径 |
| V3 | 假修复 / 假通过 | 主 agent 声明的每项修复逐条对账：已落地 / 未落地 / 无法核对；必要时设计探针反证 | 逐项三态表 |
| V4 | 行为级缺陷 | OOM / 边界 / 返回值 / 并发 / 资源释放 / 未实现 / 错误路径 | 触发条件 + 代码位置 |
| V5 | 注册点齐备 | 新增 enum / 分发表 / 回调 / 构建开关是否被接上 | 反查命中清单 |

不进 P1 的：命名、格式、缩进、死代码、魔术数字、过长函数、注释机械项、存量坏味道——这些归机械闸或 backlog。

## 文档审查范围（硬性）

审查只覆盖**归档后仍会保留**的文档；审查产出（偏离清单、文档级问题、遗留清单里的文档项）也只针对它们：

- spec、final-spec.md、`docs/architecture/`

归档时会被删除的执行期文档**不作为审查对象**，不得因它们的表述、完整性或前后不一致给出偏离、问题或 `blocked`：

- `detail/`、`exec_plans/`、`task_plan.md`、`implementation-notes.md`、`progress.md`、`findings/`

两条边界：

- **读取不受限**：这些文档仍要读——`detail/` 是一致性对照的设计基线，`implementation-notes.md` 的 Deviations / Open Questions 仍按既有规则作过程门禁（属流程门禁，不是文档审查）
- **不为它们补文档**：审查发现的问题不得转化成"补写 detail / 补 findings / 修 task_plan"这类修复项

## 范围确定规则

验收范围必须先定清楚，再开始对照。

优先级如下：

1. 用户明确指定的文件范围或提交范围
2. `ddev-plan` 中列出的文件清单
3. 当前任务对应的 git diff / 工作区 diff
4. spec / detail 文档中明确点名的实现文件

如果 exec plan 中列出的文件范围明显超出 spec / detail / flow / dataflow 文档允许的边界，也要按范围异常处理，不能默认放行。

代码评审（含清理建议）的作用范围必须继承这份范围；如果能拿到更窄的 changed-files 列表，优先进一步收敛到 changed files。

如果为了锁定既有行为必须补最小回归测试，允许把**最小必要测试文件**纳入清理附属范围；这些测试文件也必须计入清理范围说明和后续验证证据。

如果范围仍然不清楚，先输出 `need-info`，不要自己扩散成全仓库审查。

## 改动面路由

进入核心流程前，先判定本次改动面大小，决定走 streaming（流式 / 双 subagent 并行）还是 compact（整合）路线。

**默认 compact**：除命中「大改动」外，一律走 compact 整合审查。

**短路规则**：若本次改动只涉及文档、注释、格式，无行为与接口变化 → 走「机械闸 + compact」且只审 V1/V2；命中 M2 机械项的修复不再触发复审。

**判定「大改动」— 命中任一即走 streaming：**

1. diff 行数 > 300
2. grep 查到的影响范围超出本模块（存在受影响的跨模块调用方 / 文件）
3. 结构性重构：跨多文件重建结构体、数据流、状态机或公共接口，而非单文件内局部增量

**以下不单独构成「大改动」，仍走 compact：**

- 触发架构变更门禁（如「语音包可独立 OTA」这类外部可见行为变更）——架构文档只登记架构级事实（模块边界 / 职责 / 依赖 / 公共接口与协议契约），实现细节与单机型策略不写入（例外：`stdlib-wrappers*.md` 为封装对照表，保留详细描述），该补充本身是计划内小改动
- 涉及数据流 / 关键流程的局部修改——只要实现是单文件内局部增量（如新增 static 函数 + 换查表来源），API 对外签名不变
- C + Python + 文档的复合改动——按合计 diff 行数与实际影响半径判定，不因跨语言自动升级

判定依据取 spec / detail 声明的范围与 git diff / grep 查到的调用点影响范围中的**较严者**。

`ponytail: diff 行数阈值是启发式，可按团队习惯调整；与第 3 条结构性重构判定冲突时，以重构性质为准。`

## 派发方式（主 agent 专用，禁止转发给 subagent）

> 本节只给主 agent 读。**禁止**把本节或本 `SKILL.md` 的任何内容拼进 subagent 提示词——这样做的直接后果是 subagent 误认自己是主 agent，进而自行改代码、自行派生审查、并回传无法核实的审查结论。

**默认 goal 与阻塞式派发（硬性）**

- 进入本 skill 前先 `create_goal`：objective 写成本轮改动的可验证完成态（如「<本轮改动> 通过 ddev-gate 双审查 pass」）；会话 resume / fork 后 goal 会解除武装，用户说「继续」时先 `update_goal` 的 `resume` 重新武装
- 所有审查 subagent（streaming 的 A / B、compact 整合、清理）一律**阻塞式派发**，不要放到后台运行：goal 只靠当前轮推进，后台派发会让 goal 跨轮空转、白烧续跑轮次
- 同一轮要多个 subagent 时，在**同一条消息**里发出多个阻塞调用，一次等齐

**提示词裁切规则（硬性）**

- A 一致性审查：只把 `streaming-reviewer-prompt.md` **全文**作为提示词（该文件已只含 subagent 面向内容），只填写其中的「任务输入」表。
- B 代码评审：只把 `code-reviewer-prompt.md` **全文**作为提示词，同样只填「任务输入」。compact 路线用 `compact-reviewer-prompt.md`。
- 禁止把 `SKILL.md`、本节、修复/复审循环、收尾顺序、提交与归档约定等主 agent 内容拼进提示词。
- 提示词里不得出现「两个 subagent」「重跑审查」「提交」等主 agent 语义。
- 模板缺失，或模板里又混进主 agent 面向段落 → 停止派发并报告 skill 缺陷，先修模板，不要现场自制提示词。

**派发后等待（硬性）**

- 派发 subagent 后**立即停止一切工具调用**：不轮询、不空转、不反复用 `read` / `grep` / `git status` / `bash` 检查进度，也不重复派发同一审查。
- 只等待 in-session 的 subagent 完成通知／回传结果，收到后再进入汇总处置；streaming 的两个 subagent、compact 的整合 subagent、清理 subagent 一律如此。
- 同一轮要等多个 subagent 时，一次派发完就一起等，不要逐个轮询；等待本身不是审查步骤，不需要产生工具证据。

**派发后回传校验（硬性）**

- subagent 回传后先校验身份：若它宣称「派发了其它审查」「修改了文件」「重编了代码」「准备提交/归档」，该轮结论**作废**，不计入门禁证据。
- 立即用 `git status` 与文件 mtime 核对工作区是否被真实改动；被改动则视同本轮发生了代码修改，必须基于最终代码重新派发只读复审。
- 记录中只采纳主 agent 自己派发的审查 id；来源不明的 id 不得作为门禁证据。

### 模板三：compact 整合审查

#### 原模板三的派发说明（已并入本节）

- **直接把本文件全文作为整合审查 subagent 的提示词**，只填写下方「任务输入」，禁止主 agent 自行概括、改写、删减或重新生成提示词。
- 不得因为改动小或项目语言而临时发明新的审查维度、分级规则或结论规则。
- 如果本模板缺失或无法读取，停止派发并报告，不要用主 agent 现场生成的提示词替代。
- compact 路线只派发这 1 个整合审查 subagent，不得退回 streaming 的两个 subagent，也不得再单独派发清理 / 注释 / 规范审查 subagent。

（任务输入表以模板文件中的为准，派发时只填该表。）
你的任务是做一次**整合审查**，范围限定为本次小改动。你一次性完成两个维度：

1. **架构一致性**：代码实现是否偏离了文档规划的架构
2. **代码评审**：编码规范、代码质量、注释完整性（含可选的清理建议）

你输出一份合并结论。你是**只读**的：只报告问题和建议，不修改任何代码。

## 核心流程（Streaming 路线）

0. **Stop Gate 前置检查（产出遗留清单，不直接阻塞）**：主 agent 读取 `task_plan.md` 和 `implementation-notes.md`，逐项核对并**记录缺口**，然后继续验收流程：
   - 所有任务 checkbox 是否为 `[x]`（completed）
   - Errors Encountered 表中所有错误是否已解决（Resolution 列非空或已标记 Resolved）
   - `implementation-notes.md` 是否存在
   - Open Questions 是否全部回答完毕
   - 若存在 `scripts/check-complete`，运行确认输出 "ALL PHASES COMPLETE"（该脚本不存在则跳过，不算缺口）

   **分流规则**：以上缺口**不单独构成 `blocked`**，写入最终输出的「遗留清单」。只有两项例外：
   - 标注 `影响正确性: 是` 的 Open Question 未回答 → `blocked`
   - `implementation-notes.md` 缺失，且本轮确实存在需要记录的 Deviations → `blocked`

   其余（未勾 checkbox、未解决的 Error、`影响正确性: 否` 的未答项、notes 缺失但无偏离需记录）一律不阻塞，只进清单。

   **历史 notes 兜底**：早期生成的 `implementation-notes.md` 没有 `影响正确性` 字段。字段缺失时按 `是` 保守处理（即未答则 `blocked`），并在遗留清单中注明"该 notes 未使用分级字段"。

0b. **机械闸（P0）**：按 [references/mech-checks.md](references/mech-checks.md) 跑 M1~M6。
   - M1 / M4 / M5 / M6 任一 FAIL → 先修，**不派发 subagent**
   - M2 / M3 命中项 → 只作为 B 的输入，不在报告里逐条论述
   - 结果压成 `MECH: M1=.. M2=.. M3=.. M4=.. M5=.. M6=..`，随派发传给 A / B
   - M6 有改动 → 设计基线已变，按「累计漂移控制」处理
1. 主 agent 定位 spec 文档、detail 文档、架构文档、代码范围、本轮验证证据、`implementation-notes.md` 和 `task_plan.md`，整理成明确的审查上下文。
2. 主 agent 先读取 `implementation-notes.md`，提取 Deviations 和 Open Questions：
   - Deviations 条目 → 作为一致性审查的重点检查项
   - Design Decisions → 作为 spec 空白处的补充验收依据，审查 agent 需确认决策合理且未引入新的未批准架构
   - Open Questions → 按 `影响正确性` 字段分流：`是` 的未答项 → `blocked`；`否` 的未答项 → 只进遗留清单；已回答的，将其回答结论纳入验收范围
3. **同一轮并行派发两个独立 subagent（提示词必须使用固定模板、按「派发方式」的裁切规则只转发模板全文，禁止主 agent 自行生成或夹带主 agent 面向内容）**。为保证两个审查读到同一份稳定代码，本轮两个 subagent 都只读、不修改文件；清理在评审返回后由主 agent 执行：
   - **A. 一致性审查**（只读）：直接使用 [streaming-reviewer-prompt.md](streaming-reviewer-prompt.md) 全文作为提示词，只填写其中的任务输入；只核对代码与文档规划架构的一致性，输出偏离清单。
   - **B. 行为评审**（只读）：直接使用 [code-reviewer-prompt.md](code-reviewer-prompt.md) 全文作为提示词，只填写其中的任务输入；只报会改变行为的缺陷 + 假修复对账 + 机械闸结果解读；复审轮必须做影响面兜底（`IMPACT`）。
4. 等待两个 subagent 返回（**禁止轮询/死等**：派发完成后停止工具调用，只等完成通知，不得反复调用工具检查进度或空转等待，规则见「派发方式」的派发后等待）：
   - A 输出 `VERDICT` / `IMPACT` / 架构偏离清单（每项标 **修正** 或 **记录**），并回执 `DEV-ID` 闭环表
   - B 输出 `VERDICT` / `SEV` / `IMPACT` / `ESCALATE`，附行为问题分级、M2 摘要、假修复三态表
   - 两者缺 `IMPACT` 行 → 报告不完整，不得据此给 `pass`
5. 主 agent 汇总处置（按级别分流，别一次全修）：
   - **CRITICAL / HIGH 行为问题 + 注释与代码矛盾**：立即修；每项登记 `DEV-ID`，复审时按 ID 对账（见「Deviations 闭环」）。
   - **MEDIUM / LOW**：只进 backlog（`implementation-notes.md` 的 Backlog 段），**不触发复审**，终轮一次性处理。
   - **A 报出的偏离**：可修正的立即修正；无法修正的写入 Deviations，给 `DEV-ID` + 理由 + 影响面 + 复核轮。
   - **清理建议**：默认不进本轮，随 backlog 在终轮按 `ddev-clean` 规则处理；若在 gate 期间执行了清理，必须补验证证据并按 P2 兜底规则复审。
   - 任何代码修改后补验证证据（沿用清理前的旧证据不算）。
6. **增量复审规则（不是全量重跑）**：
   - B 复审范围 = 本轮 diff + 上一轮未闭环 `DEV-ID` + 影响面兜底结果（见「复审兜底」）。
   - A 复跑条件（满足其一）：改动触及模块边界 / 公共接口 / 依赖方向 / 状态所有权 / 注册表；M6 检测到文档基线变更；累计漂移超阈值（见「累计漂移控制」）。
   - 纯注释 / 格式 / 死代码 / 魔术数字类改动，不触发 A。
   - 复审轮两个 subagent 仍然只读，只验证最终状态。
7. **收敛与轮次预算**：同一任务最多 3 轮（首轮 + 2 次复审）。达成「双方 pass + 本轮无修改」即收口；第 3 轮结束仍不收敛 → 输出 `need-info` + 遗留清单 + 未闭环 `DEV-ID` 表，交用户裁决，禁止自行开新一轮。
8. 下列情况直接 `blocked`：
   - A 报出的架构偏离既未修正，也未写入 `implementation-notes.md` 记录；
   - B 存在未处理的 CRITICAL / HIGH 行为问题，或注释与代码行为矛盾未处理；
   - 清理过程改变了文档已批准的架构、接口或行为，且未回退、未重新走双审；
   - **影响面兜底发现未审的受影响文件**（`IMPACT: delta>0`）；
   - **累计漂移超阈值且未重新锚定**；
   - 两个审查无法在同一份最终代码上同时通过。
9. **证据分级**：没有 `repro` 级证据（构建 / 仿真 / 真机可复现）时最多 `need-info`；静态核对（grep / read）只能支撑 `pass-static`，不能作为最终 `pass`。

## Compact 路线（小改动）

改动面路由判定为小改动时走本路线。核心原则：**1 个独立 subagent 一次性完成两个维度**，不派发第二个 subagent，不单独调用 `ddev-clean`。

C0. **前置检查**：同 Streaming 步骤 0，产出遗留清单并按同一规则分流。只有「`影响正确性: 是` 的 Open Question 未答」或「notes 缺失且确有偏离需记录」才 `blocked`；其余记账缺口进清单，不阻塞。
C1. 主 agent 定位 spec、detail、架构文档、代码范围、本轮验证证据、`implementation-notes.md` 和 `task_plan.md`，读取并整理成审查上下文。
C2. 主 agent 读取 `implementation-notes.md`，提取 Deviations（作为一致性重点检查项）、Design Decisions（作为 spec 空白处补充依据）、Open Questions（未答 → `blocked`）。
C3. 拉 **1 个独立 subagent** 做整合审查：**直接使用 [compact-reviewer-prompt.md](compact-reviewer-prompt.md) 全文作为提示词，只填写其中的任务输入，禁止主 agent 自行生成或改写提示词**。该 agent **只读**，一次性完成：
    - **一致性对照**：只核对代码与文档规划架构的一致性（模块边界、接口、依赖方向、状态归属、数据流/流程骨架），输出偏离清单并标注建议处置（修正 / 记录）；**先用 `grep`/`read` 看影响面与需审查文件**，影响面超出 spec/detail 声明范围视为偏离
    - **行为评审**：只报会改变行为的缺陷 + 假修复对账；注释只报与代码行为矛盾项；清理清单仅终轮输出
    - 输出 `VERDICT` / `SEV` / `IMPACT` / `SCOPE` 机读头 + 偏离清单 + 行为问题分级 + `DEV-ID` 闭环表
C4. 主 agent 汇总处置（同 Streaming 步骤 5 的分流规则）：
    - CRITICAL / HIGH 行为问题 + 注释与代码矛盾：立即修，登记 `DEV-ID`
    - MEDIUM / LOW 与清理建议：只进 backlog，不触发复审，终轮一次性处理
    - 架构偏离：能修则修；不修则写入 Deviations（`DEV-ID` + 理由 + 影响面 + 复核轮）
C5. **增量复审**：复审只审本轮 diff + 未闭环 `DEV-ID` + 影响面兜底（见「复审兜底」）；预算 3 轮。纯注释 / 格式类改动不触发全量重扫。
C6. `blocked` → 主 agent 按清单修改，从 C3 复审（不升级为 Streaming）；第 3 轮仍不收敛 → `need-info` + 遗留清单。
C7. `need-info` → 补齐缺失输入 / 范围 / 验证证据后从 C3 重跑。
C8. `pass` → 满足「结论规则」中 compact 条件后，主 agent 才能宣称"已经按计划完成"。

Compact 路线同样要求 spec、detail、代码范围、验证证据齐全，缺任何一项都不能给 `pass`。Compact 整合审查 agent 只读，不得在审查过程中修改代码。

## 复审兜底（P2：B 只审 diff 时如何不漏影响面）

增量复审的风险是"只看 diff 就放行"。三层兜底，缺一层都不算做过复审。

### 1. 影响面再推导（每轮必做）

- 输入：本轮 diff 的变更符号（函数 / 宏 / 结构体 / 枚举 / 全局变量）+ 改动文件清单
- 动作：对每个变更符号反向 `grep` 调用方与引用点；对每个 `.h` 列出 `include` 方；把得到的受影响文件集合与 `gate-scope.yaml` 的 `impact_surface.callers` 对账
- 输出：`IMPACT: checked=<n> delta=<n>` + delta 文件清单
- 判定：`delta > 0` → B **不得给 pass**，转 `need-info`，并要求补跑 A（一致性）覆盖 delta 文件

### 2. 高扇出载体自动升级全量（命中任一即全量）

- 公共头文件 `.h`（被多个文件 include）
- 注册表 / 枚举 / 分发表 / 回调表 / 事件表 / 命令表
- 构建脚本、Makefile、链接脚本、分区表、编译宏
- 全局状态结构体、跨模块导出符号
- diff 中出现**新增文件**或**删除文件**

命中后强制跑全量 A + B，不得用增量结论收口。

### 3. 工作区全量对账（每轮必做一次）

- `git status --porcelain` 必须与 diff 范围一致；存在未跟踪 / 未暂存文件且不在 scope 清单 → 记为 `SCOPE_DRIFT`
- spec / detail / `docs/architecture/` 被改动 → 按 M6 处理，升级全量 A

B 复审报告必须输出 `IMPACT` 行与 delta 清单；缺这一行视为报告不完整，主 agent 不得据此给 `pass`。

## 累计漂移控制

**问题**：每轮只审 diff，N 轮后代码可能已整体偏离 spec，而每轮单独看都"没问题"；更危险的是修复过程中改文档去适配实现。

**机制**：

1. **锚点**：首轮审查时把 `git rev-parse HEAD`（无提交则 `git stash create` 的 hash）写入 `gate-scope.yaml` 的 `baseline.ref`，同时记录首轮声明规模（文件数 / 行数）。
2. **累计 diff 对账**（终轮必做）：
   - `git diff <baseline>` 的累计文件集 vs `planned_files` + `allowed_globs`
   - 累计改动行数 vs 首轮声明规模
   - 累计新增符号清单 vs spec / detail 的接口表
3. **漂移预算**：
   - 文件增量 ≤ 计划文件数 50% 且 行数 ≤ 2 倍 → 允许增量复审
   - 超出任一 → 强制全量 A + B，并在报告列出 `DRIFT` 表（文件 / 行数 / 新增符号）
4. **文档基线漂移**（最危险）：gate 期间 spec / detail / `docs/architecture/` 被修改 → 必须显式声明为「设计变更」；未声明 → `blocked`；声明后重跑 A 全量，该轮**不计入 3 轮预算**。
5. **收口陈述**：最终 `pass` 必须附 `DRIFT: files=<+/-><n> lines=<+/-><n> baseline=<ref>`，并说明"终轮已核对累计 diff"。

## Deviations 闭环

- 每条偏离给 `DEV-ID`（`DEV-<任务短名>-<序号>`）
- 必填：偏离点 / 理由 / 影响面 / 处置（修正 | 记录 | 不接受）/ 复核轮
- 复审报告必须输出「待闭环 DEV-ID 表」（ID + 上轮状态 + 本轮判定）
- 同一 `DEV-ID` 连续 2 轮"记录但未复核" → 升级 `blocked` 或提交用户裁决，禁止无限记录

## 机读输出契约

主 agent 最终输出的**第一块**必须是机读头，其后才是自然语言结论：

```
VERDICT: pass | need-info | blocked
SEV: C=<n> H=<n> M=<n> L=<n>
SCOPE: changed=<n> out_of_scope=<n> scope_source=plan|derived
IMPACT: checked=<n> delta=<n>
DRIFT: files=<+|-><n> lines=<+|-><n> baseline=<ref>
EVIDENCE: repro | static
ROUND: <n>/3
```

- subagent 报告同样以 `VERDICT:` 开头，**只允许单一 token**（禁止 `pass（附建议）` 这类写法）
- `need-info` 必须附「缺什么」，`blocked` 必须附「改什么」
- 机械闸摘要作为附录，形如 `MECH: M1=pass M2=3hit M3=2hit M4=pass M5=pass M6=pass`

## 审查 agent 要求

> **通用规则**：所有审查 agent 评估改动影响面时，一律**先用 `grep`/`read` 看影响面与需审查文件**。

> **提示词模板硬性要求**：streaming 路线必须直接把 [streaming-reviewer-prompt.md](streaming-reviewer-prompt.md) 全文用作一致性审查提示词，把 [code-reviewer-prompt.md](code-reviewer-prompt.md) 全文用作代码评审提示词；compact 路线必须直接把 [compact-reviewer-prompt.md](compact-reviewer-prompt.md) 全文用作整合审查提示词。主 agent 只填写模板里的「任务输入」，禁止自行生成、概括、改写或拼装审查提示词；模板缺失或无法读取时停止派发并报告，不得用现场生成的提示词替代。

### 一致性审查 agent 要求

- 必须是独立视角，只读，不能把主 agent 自己的口头总结当结论
- **只审查架构一致性**：模块边界与职责、接口位置与签名、调用/依赖方向、状态所有权、数据流与关键流程骨架、联动注册点、文档批准的共享状态与全局变量边界
- 必须显式核对 spec、detail / 架构文档、代码事实三类输入，以及 `implementation-notes.md` 中的 Deviations
- **先用 `grep`/`read` 看影响面与需审查文件**：确认实际影响范围与文档声明一致；存在文档未声明的受影响模块或新增跨模块耦合 → 视为偏离
- 每个偏离必须给出：文档依据、代码事实、位置、建议处置（修正 / 记录）
- 不检查 exec plan 的逐步落地，不检查命名、风格、注释、测试覆盖、代码质量；这些分别归文档计划和代码评审负责
- 不允许用“基本一致”“差不多符合”“核心没问题”这类模糊表述放行
- 如果本轮代码已经过清理或修复，必须按**最终代码**重做对照，不能沿用上一轮结论

一致性审查必须原样使用提示模板 [streaming-reviewer-prompt.md](streaming-reviewer-prompt.md)，主 agent 只填写模板中的任务输入，不得自行生成提示词。

### 代码评审 agent 要求

必须是独立视角，不能复用一致性审查 agent 的结论。按项目语言路由，**一次性合并**以下维度，输出一份结论：

- **C 项目（`.c` / `.h`）**：加载 `ddev-c-pro`（编码规范 + 代码质量：安全、架构性能、死代码/重复）+ `ddev-comment-gen`（注释完整性）+ `ddev-clean`（清理项识别，只出清单）。不再单独调用 `ddev-code-review`，也不再有单独 c-pro / comment-gen 阶段。
- **非 C 项目**：加载 `ddev-code-review`（代码质量）+ 对应语言编码规范 skill（如有）+ 对应注释审查 skill（如有）+ `ddev-clean`（清理项识别，只出清单）。没有对应 skill 的维度在结论中标注“已跳过”。
- **先用 `grep`/`read` 看影响面与需审查文件**：确认审查范围覆盖所有受影响文件。
- **问题分级**：CRITICAL（安全漏洞 / 崩溃）> HIGH（行为 Bug）> MEDIUM（技术债）> LOW（建议）。只有 CRITICAL / HIGH **行为问题** → `blocked`；规范、格式、死代码、魔术数字、过长函数一律不阻塞。
- **注释**：机械项（`@file`/`@brief`、Doxygen、英文注释、术语泄漏、`#if 0`、冗余 `extern`）由机械闸 M2 覆盖，报告只写 M2 摘要；B 只报**注释与代码行为矛盾**（唯一可阻塞的注释项）。
- **清理**：首轮 / 复审轮不输出清理清单；终轮输出一次 backlog，由主 agent 一次性决定是否执行。清单不得改变行为、接口、架构。执行清理后按增量复审规则处理（触及架构面才重跑 A）。
- **假修复对账**：复审轮必须对主 agent 声明的每项修复给三态（已落地 / 未落地 / 无法核对），不得笼统写"已修复"。
- **任何轮次都只读**：代码评审 subagent 不修改代码；复审轮重点验证上一轮修复 / 清理的最终状态。
- 不允许用"基本规范""大体符合""基本齐全"等模糊表述放行。
- 如果代码经过修复或清理，必须基于最终版本重新审查，不能沿用前次结论。

代码评审必须原样使用提示模板 [code-reviewer-prompt.md](code-reviewer-prompt.md)，主 agent 只填写模板中的任务输入，不得自行生成或改写提示词。

### Compact 整合审查 agent 要求

（compact 路线专用；Streaming 路线使用上方两个独立 agent）

- 必须是独立视角，只读，不能复用主 agent 的口头总结
- **一次性完成两个维度的审查**，输出一份结论：
  1. **一致性**：只核对代码与文档规划架构的一致性（模块边界、接口、依赖方向、状态归属、数据流/流程骨架）；显式核对 Deviations 的处置状态；**先用 `grep`/`read` 看影响面与需审查文件**，影响面超出 spec/detail 声明范围视为偏离
  2. **行为评审**：只报会改变行为的缺陷（安全 / 崩溃 / 边界 / 返回值 / 并发 / 未实现），按 CRITICAL / HIGH / MEDIUM / LOW 分级；注释只报与代码行为矛盾项；清理建议仅终轮输出
- 结论只允许 `pass` / `need-info` / `blocked`
- 不允许用"基本一致""大体符合"等模糊表述放行
- 如果代码经过主 agent 修复或按建议清理后重审，必须基于最终版本重新审查，不能沿用前次结论

compact 整合审查必须原样使用提示模板 [compact-reviewer-prompt.md](compact-reviewer-prompt.md)，主 agent 只填写模板中的任务输入，不得自行生成或改写提示词。

## 重点检查项

默认重点检查（架构一致性）：

- 模块边界、模块职责是否与 spec / `docs/architecture/` 一致
- 接口位置、调用方向、接入点是否与 spec 设计一致
- 结构体归属、字段 ownership、状态所有权是否与 detail / structures 文档一致
- 数据流入口、转换、出口，以及关键流程骨架、状态迁移、错误路径是否与 detail 文档一致
- 联动注册点（分发表、回调表、枚举映射、构建目标等）是否与 spec 的联动修改清单一致
- 是否新增了文档未批准的跨模块依赖、共享可变状态或业务全局变量
- 是否破坏文档约定的 `static` 私有边界、`switch` / 表驱动 / 状态机结构
- 架构偏离是否已修正，或已写入 `implementation-notes.md` 的 Deviations

不再由一致性审查负责的项：

- exec plan 的每个步骤是否落地（属于执行记录）
- 命名、风格、编码规范（属于代码评审）
- 注释完整性（属于代码评审）
- 测试覆盖、构建结果（属于验证证据，由主 agent 在结论中核对）

对于嵌入式 C / 纯 C 项目，额外重点检查：

- 运行时状态是否确实收敛到 `context` / session / handle 结构体
- 状态值是否使用 `enum` 或等价显式语义，而不是魔法数字
- 分发方式是否符合设计时选定的守卫式返回、`switch`、表驱动或状态机
- `static` 私有函数边界是否与文档设计一致
- 错误码、异常出口和资源清理路径是否与设计一致

## 注释问题分级（与 `ddev-comment-gen` 共用口径）

注释问题并入代码评审结论，分级口径在 `ddev-gate` 与 `ddev-comment-gen` 必须一致，不另立标准。

**分流原则：机械项进 M2 脚本，语义项进 P1，裁量项只进 backlog。**

| 类别 | 情形 | 谁判定 | 判定 |
|------|------|--------|------|
| 机械 HIGH | 文件头 `@file`/`@brief` 缺失；`.h` 公开函数 Doxygen 缺失（`@brief`/`@param`/`@return`）；公开 `struct`/`enum` 的 `@brief` 缺失；术语泄漏 grep 命中 | M2 脚本 | 修完再派发 |
| 机械 MEDIUM/LOW | 成员注释缺失、英文注释、冗余注释、注释掉代码、`#if 0`、悬空注释 | M2 脚本 | 只进 backlog |
| 语义 HIGH | **注释与代码行为矛盾**（含"注释声称的契约与实现不符"） | P1（B） | `blocked` |
| 语义 MEDIUM | 注释复述代码、超长块注释、注释与文档口径冲突 | P1（B） | 只进 backlog |

判据说明：

- **错误注释 > 缺失注释**：注释与行为矛盾会让读者按错误理解改代码；缺失只是信息不足
- 机械项的判定权下放给脚本：审查报告不再逐条论述，只写「M2 命中 N 项，已修 / 进 backlog」
- 语义项必须给位置与反例（读代码后能复现的矛盾），不接受"感觉不一致"
- MEDIUM / LOW 不阻塞 `pass`，进 backlog；**不再要求同轮补齐**（补齐会触发重审，是过去的轮次膨胀主因）

详细检查清单见 [acceptance-checklist.md](references/acceptance-checklist.md)。

标准输出样例见 [example-acceptance-output.md](examples/example-acceptance-output.md)。

## 结论规则

只允许输出这三种最终结论：

- `pass`
- `need-info`
- `blocked`

compact 路线同样只允许这三种结论；两个审查维度由 1 个整合 subagent 一次性覆盖。

### `pass`

只有在以下条件同时满足时才能给：

- 已找到并核对 spec 文档
- 已找到并核对 detail / 架构文档
- 已明确本轮验收对应的代码范围
- **一致性**：代码与文档规划的架构一致，或每一处偏离都已修正、或已写入 `implementation-notes.md` 的 Deviations 且理由和影响范围清楚
- **行为评审**：无未处理的 CRITICAL / HIGH 行为问题；无注释与代码行为矛盾；假修复对账无"未落地"项；终轮 backlog 已给出（或无需清理）；如执行了清理，清理未改变架构、接口、行为且已补验证证据
- **最终轮**：最后一轮中一致性审查与代码评审在同一份最终代码上都 `pass`，且该轮没有任何代码修改；若此前发生过修改，已完成只读复审
- 本轮存在新的验证证据，且为 `EVIDENCE: repro`（构建 / 仿真 / 真机）；仅静态核对最多给 `pass-static`
- **影响面兜底已完成**：`IMPACT: delta=0`，或 delta 项已补审并闭环
- **累计漂移已对账**：`DRIFT` 在预算内，或超预算后已重跑全量审查
- **机械闸无 FAIL**：M1 / M4 / M5 / M6 全 pass（M2 / M3 命中项已修或进 backlog）
- 未覆盖风险已明确说明
- **遗留清单已输出**：task_plan checkbox、Errors 表、`implementation-notes.md`、Open Questions 的缺口状态已随结论列出（缺口本身不阻塞 `pass`，判定口径只在步骤 0 定义一处，此处不重复列举）
- 如果 `implementation-notes.md` 中存在 Deviations，每一项都已给出结论（已修正 / 已接受并记录 / 需补文档）

### `need-info`

用于信息不足但还不构成硬阻塞的情况，例如：

- 缺少部分 detail 文档
- 缺少关键验证结果
- 没有新的验证证据，无法支撑 `pass`
- 改动范围无法唯一确定
- 某些实现意图在代码里存在，但文档没有明确写
- 设计与实现差异无法判断是故意还是遗漏
- 遗留清单中积累了较多未清的文档记账项，且其中部分无法判断是否影响正确性

判定原则：

- 还能通过补文档、补范围、补验证证据继续推进的，用 `need-info`
- 当前虽然不能给 `pass`，但继续核对仍然有意义的，用 `need-info`

### `blocked`

用于无法验收或明显不通过的情况，例如：

- 找不到 spec 文档或 detail 文档
- `implementation-notes.md` 缺失且存在需要记录的 Deviations；或标注 `影响正确性: 是` 的 Open Question 未回答
- 无法定位本轮改动对应的实现范围
- 代码偏离文档规划的架构，且既未修正、也未写入 `implementation-notes.md`
- 一致性审查与代码评审无法在同一份最终代码上同时通过
- 代码评审存在 CRITICAL / HIGH 问题未处理
- 存在注释与代码行为矛盾（机械项由 M2 先行拦下，未修完不应派发）
- 清理过程改变了文档已批准的架构、接口或行为，且未回退、未重新走双审
- 结论依赖关键证据，但证据不存在
- `task_plan.md` 缺失或不在计划目录下，导致无法确定本次改动的任务范围（属结构性输入缺失，与「未勾 checkbox」的记账缺口不同）

判定原则：

- 关键设计基线缺失、互相冲突或当前上下文下无法建立时，用 `blocked`
- 在补齐前提之前继续审查没有意义的，用 `blocked`
- 只要需要打回主 agent 改代码或改文档后再审，也用 `blocked`

## 输出格式

最终输出必须包含：

0. **机读头**（见「机读输出契约」，必须第一块，含 VERDICT / SEV / SCOPE / IMPACT / DRIFT / EVIDENCE / ROUND）
1. 验收结论：`pass` / `need-info` / `blocked`
2. 对照范围：看了哪些 spec / detail / 架构文档 / implementation-notes / code / 验证材料
3. 并行审查摘要：
   - 一致性审查结论：架构是否一致、`IMPACT` 是否闭合
   - 行为评审结论：问题分级汇总（C/H/M/L 各几条）、M2 摘要、假修复对账结果
   - 机械闸摘要：`MECH: M1=.. M2=.. M3=.. M4=.. M5=.. M6=..`
4. **遗留清单**（不阻塞项，但必须列出）：
   - 文档记账缺口：未勾的 checkbox、未解决的 Error、`implementation-notes.md` 缺失、未答 Open Question（含 `影响正确性` 取值）
   - backlog：M2 / M3 命中项、终轮清理建议、未闭环 `DEV-ID`
   - 漂移说明：累计 diff 是否超预算、是否已重锚定
5. 架构偏离处置表：

   | 偏离点 | 文档依据 | 处置（已修正 / 已记录 / 未处理） | 位置 |
   |--------|----------|----------------------------------|------|

6. 发现的问题：按严重度列出
7. 已确认一致的关键点：只列最重要的几项
8. 未覆盖风险：明确还没验证到哪里
9. 清理与修复说明：是否改过代码、范围是什么、验证证据是什么、是否已完成只读复审
10. 如果结论是 `blocked`，明确列出“需要主 agent 修改的项”，以便按项修复并重新送审

**compact 路线**：第 3–5 项合并为一份「整合审查结论」，一次性输出一致性 + 代码评审两个维度的结果和偏离处置表；遗留清单同样必须列出。

如果没有发现不一致，也不能只说“通过”，仍要说明对照了什么。

如果需求结论依赖真实目标板、外设、时序、功耗、波形或现场观察，而本轮没有对应人工或现场证据，不能给 `pass`。

## 与其他 skill 的关系

- 上游通常来自 `ddev-spec`、`ddev-detail`、`ddev-plan`、`ddev-exec`
- **改动面清单**由 `ddev-plan`（计划定稿时生成）与 `ddev-exec`（执行中维护）产出，本 skill 只消费不生成
- 如需补验证证据，联动 `verification-before-completion`
- **一致性审查**由本 skill 直接派发独立 subagent
- **代码评审**合并以下 skill 的职责，由本 skill 派发的代码评审 subagent 统一加载：
  - `ddev-code-review`（非 C 项目的代码质量维度；也可独立触发）
  - `ddev-c-pro`（C 项目的编码规范 + 代码质量维度）
  - `ddev-comment-gen`（C 项目的注释审查维度）
  - 对应语言的编码规范 / 注释 skill（非 C 项目，如有）
  - `ddev-clean`（清理项识别维度；清理执行由主 agent 按需调用，也可独立触发）
- **compact 路线**：小改动由 1 个整合审查 subagent 一次性覆盖一致性 + 代码评审；不单独调用 `ddev-clean`
- 默认在 `ddev-exec` 的末尾作为最终收口门禁

### ⚠️ 阶段交接硬门禁

**本 skill 完成后，禁止 agent 自动进入任何后续阶段（ddev-archive / git commit / 发布 / 部署 等）。**

- gate 最终 `pass` 后，向用户报告完整的验收结论（一致性、代码评审、清理）。
- 提示用户可选后续操作（如"是否提交代码？""是否进入 ddev-archive 归档？"），但**必须等待用户明确确认**。
- 用户未明确说"提交""归档""发布""推送"等指令前，停留在 gate 结论输出阶段，不自行推进。
- gate 内部的「并行审查 → 修复/清理 → 只读复审」循环为自动化流程，不受此限制。

## 最低要求

没有 spec 文档、没有 detail 文档、没有代码对照，就不要假装做了最终验收。

验收的重点是：**实现是否符合文档规划的架构** + **合并后的代码评审是否通过**，不是只看"代码能不能跑"。

streaming 路线必须真正做到两个 subagent 并行派发；最终放行对象必须是两个只读复审 subagent 在同一份最终代码上共同 `pass` 的那一版代码，不是任何中间版本。

机械闸不是可选项：M1（范围）/ M4（注册点）/ M5（证据）/ M6（文档基线）任一 FAIL 时派发审查等于浪费一轮。

放行底线是：**无未处理的 CRITICAL / HIGH 行为问题、无注释与代码行为矛盾、`IMPACT` 与 `DRIFT` 已对账**。规范化、格式、注释机械项、清理建议一律只进 backlog，不卡放行。

**compact 路线**：同样必须有 spec、detail、代码范围、验证证据；整合 subagent 通过（覆盖一致性、代码评审、清理建议）才能给最终 `pass`，不因改动小而降低底线。
