# 实现最终验收检查清单

这个清单用于 `ddev-gate` 的详细对照。

核心结构：**一致性审查**只核对代码与文档规划架构的偏离；**代码评审**一次性覆盖编码规范、代码质量、注释完整性和受限清理。大改动同时派发两个独立 subagent；小改动由 1 个整合 subagent 一次完成。

默认规则：design 文档只声明”这次要做什么”。凡是 spec、detail 中没有明确写到的**架构**内容，默认按未批准处理；文档没写、属于实现自由度的细节不算架构偏离。

## 1. 输入完整性

- 是否已经定位本次改动对应的 spec 文档
- 是否已经定位本次改动对应的 detail / 架构文档（structures / dataflow / flows）
- 是否已经定位实际代码改动范围
- 是否拿到了必要的验证证据（本轮新证据）
- 是否读取了 `implementation-notes.md`（Deviations / Design Decisions / Open Questions）
- 是否读取了 `task_plan.md`，且所有任务完成、错误已解决
- 如果本轮发生过清理或修复，是否已记录最终代码范围和清理后的验证证据
- exec plan 仅用于确定范围和任务背景，不作为架构真源

缺任何关键项，都不能直接给 `pass`。

如果 spec / detail / 代码范围三者之一无法唯一定位，应停止一致性验收，不要退化成泛化 review。

## 2. 架构一致性检查

- 模块边界、模块职责是否与 spec / `docs/architecture/` 一致
- 接口位置、接口签名、接入点是否与 spec 设计一致
- 调用方向和依赖关系是否与设计一致，是否新增未批准的跨模块耦合
- 结构体归属、字段所有权是否与 detail / structures 文档一致
- 配置、运行时状态、输入、输出是否按文档拆分
- 运行时状态是否收敛到文档指定的 context / session / handle 对象
- 数据流入口、转换、出口是否与 detail / dataflow 一致
- 主流程骨架、状态迁移、错误路径是否与 detail / flows 一致
- 是否新增文档未说明的旁路逻辑、共享可变状态、业务全局变量
- 联动注册点（分发表、回调表、枚举映射、编译/构建开关）是否与 spec 的联动清单一致
- 影响面是否超出文档声明范围（用 code-review-graph + grep 核对）

## 3. 架构偏离处置

发现偏离时逐项确认：

- 能修正的偏离，是否已修正到与文档一致
- 无法修正或主 agent 决定不修正的偏离，是否已写入 `implementation-notes.md` 的 Deviations，且包含偏离点、理由、影响范围
- 是否仍存在“既未修正、也未记录”的偏离（存在 → `blocked`）
- 清理过程是否引入了新的包装层、抽象层、文件结构变化或范围外重构（存在 → 视为架构偏离）

不要把所有差异都归类成“小问题”。

## 4. C 结构纪律（仅 `.c` / `.h`）

- 是否新增业务全局变量
- 是否出现长链 `if/else`
- 是否用魔法数字表示状态
- 是否把多类职责塞进单函数
- 是否违反文档约定的 `switch` / 表驱动 / 状态机方案
- 是否破坏 `static` 私有边界
- 错误码、异常出口、资源清理路径是否与设计一致

## 5. 代码评审（规范 + 质量 + 注释）

代码评审由独立的代码评审 subagent 完成（streaming 与一致性审查并行；compact 与一致性合并为一次整合审查）。按项目语言路由：

- **C 项目**：加载 `ddev-c-pro`（编码规范 + 代码质量：安全、架构性能、死代码/重复）、`ddev-comment-gen`（注释完整性）、`ddev-clean`（清理项识别，只出清单）
- **非 C 项目**：加载 `ddev-code-review` + 对应语言编码规范 skill（如有）+ 对应注释审查 skill（如有）+ `ddev-clean`（清理项识别）；无对应 skill 的维度标注“已跳过”

检查要点：

- 编码规范：全局变量必要性、参数封装、命名与前缀、错误处理、内存 ownership、风格一致性
- 安全：硬编码凭据、缓冲区溢出、注入、路径遍历、整数溢出、敏感数据泄露
- 架构性能：N+1 模式、算法选择、循环内重复分配
- 死代码 / 不可达分支 / 跨文件重复
- 注释：文件头 `@file`、公开函数 Doxygen、结构体 / 枚举成员注释、关键逻辑注释、注释与行为一致性、注释语言
- 问题分级：CRITICAL / HIGH 阻塞；MEDIUM / LOW 不阻塞
- 注释缺失阻塞，必须附缺失清单；无对应注释 skill 时标注“已跳过”

## 6. 清理检查（已并入代码评审）

- 清理是否遵守 `ddev-clean` 的 regression-tests-first、显式清理计划、分 smell 分 pass、最小 diff、最小作用域
- 清理是否改变了外部行为、公开接口、函数签名、文档已批准的架构 / 数据流 / 状态所有权（改变 → 必须回退或重新走双审）
- 是否借清理扩大了改动范围、引入新抽象层或新依赖
- 清理后是否重新运行验证，并对触及文件复核评审结论
- 只读复审轮是否确实没有产生任何代码修改

## 7. 验证证据

- 构建是否通过
- 静态检查是否通过
- 测试是否覆盖关键路径
- 人工验证是否覆盖硬件或现场行为
- 证据是否真的对应本次结论
- 这些证据是否是本轮新的有效证据，而不是历史残留结果
- 如果发生过清理或修复，是否拿到了最终代码对应的新证据

如果结论依赖人工确认但没有人工证据，只能降级。

如果没有本轮新的有效证据，不能给 `pass`。

## 8. 最终轮与输出约束

- 最终 `pass` 必须对应一轮：两个审查在同一份最终代码上都通过，且该轮无任何代码修改
- 只要发生过代码修改，是否已基于最终代码完成只读复审
- 最终必须明确：
  - 结论是 `pass`、`need-info` 还是 `blocked`
  - 架构偏离清单及每项处置（已修正 / 已记录 / 未处理）
  - 代码评审结论：问题分级汇总、注释完整性、清理是否执行及是否改变行为/架构
  - 哪些点已确认一致
  - 哪些风险未覆盖
  - 是否已明确列出打回主 agent 的修改项

## 9. `need-info` 与 `blocked` 分流

- 缺信息但补齐后还能继续验收：`need-info`
- 基线冲突、关键文档缺失、未处理的架构偏离、CRITICAL/HIGH 未修、注释缺失未补、清理越界未回退，或前提不成立导致继续验收没有意义：`blocked`

不要把所有“不够确定”都打成 `need-info`。
