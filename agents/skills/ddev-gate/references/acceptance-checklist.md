# 实现最终验收检查清单

这个清单用于 `ddev-gate` 的详细对照。

默认规则：design 文档只声明”这次要做什么”。凡是 spec、detail、exec plan 中没有明确写到的实现内容，默认按未批准处理，不要求文档再额外列一份”明确不做”清单。

## 1. 输入完整性

- 是否已经定位本次改动对应的 spec 文档
- 是否已经定位本次改动对应的 detail 文档
- 是否已经定位本次改动对应的 exec plan
- 是否已经定位实际代码改动范围
- 是否拿到了必要的验证证据
- 如果经过 `ddev-clean`，是否已确认 cleanup 的实际修改范围与最终代码状态

缺任何关键项，都不能直接给 `pass`。

如果 spec / detail / 代码范围三者之一无法唯一定位，应停止一致性验收，不要退化成泛化 review。

## 2. spec 一致性

- 模块职责是否与 spec 文档一致
- 模块边界是否与架构图一致
- 接入点是否与 spec 设计说明一致
- 调用方向和依赖关系是否与设计一致
- 是否新增了 spec 文档未提及的跨模块耦合

## 3. 结构体与状态一致性

- 结构体定义是否与 detail 文档一致
- 字段归属是否一致
- 配置、运行时状态、输入、输出是否按文档拆分
- 运行时状态是否收敛到上下文对象
- 是否出现文档未批准的共享可变状态

## 4. 数据流与流程一致性

- 主流程是否与 detail 文档或流程图一致
- 数据流入口、转换、出口是否一致
- 状态迁移是否一致
- 错误路径是否一致
- 是否新增文档未说明的旁路逻辑
- exec plan 要求的关键实现步骤是否真的落地
- 是否出现计划里明确要求、但代码里漏做的环节
- 如果经过 `ddev-clean`，清理后的代码是否仍保持上述一致性

## 5. C 结构纪律

- 是否新增业务全局变量
- 是否出现长链 `if/else`
- 是否用魔法数字表示状态
- 是否把多类职责塞进单函数
- 是否违反文档约定的 `switch` / 表驱动 / 状态机方案
- 是否破坏 `static` 私有边界
- 清理过程中是否引入了新的包装层、抽象层或范围外重构

## 6. 偏离判断

如果实现与文档不一致，必须明确归类：

- 文档过时，实现合理
- 实现偏离设计，需要修代码
- 实现偏离 exec plan，需要修代码
- 设计本身不完整，需要补文档
- 当前证据不足，不能判断

不要把所有差异都归类成“小问题”。

## 7. c-pro 代码规范审查

c-pro 审查由独立 subagent 加载 `c-pro` skill 完成，与一致性验收分开执行。审查要点：

- 全局变量：是否必要？状态是否已封装到结构体中通过 context pointer 传递
- 函数参数：超过 4–5 个时是否用结构体封装
- 注释：公开 API 是否有 Doxygen 注释（`@brief` / `@param` / `@return`），文件头是否有 `@file`
- 命名：类型是否用 `_t` 后缀、公开 API 是否有统一模块前缀、宏是否全大写
- 错误处理：是否用显式返回码而非依赖 errno、公开 API 是否校验输入参数
- 内存：ownership 是否明确、是否优先由调用方传 buffer + capacity
- 风格：缩进、大括号、行宽、指针 `*` 位置是否与 c-pro 偏好一致
- 静态检查：`static` 是否用于限制内部符号可见性、`const` 是否用于只读数据

c-pro 审查结论只允许 `pass` 或 `blocked`，`blocked` 必须附修改项清单。

## 8. 验证证据

- 构建是否通过
- 静态检查是否通过
- 测试是否覆盖关键路径
- 人工验证是否覆盖硬件或现场行为
- 证据是否真的对应本次结论
- 这些证据是否是本轮新的有效证据，而不是历史残留结果
- 如果 cleanup 改了代码，是否拿到了 cleanup 后的新证据，而不是沿用 cleanup 前结果

如果结论依赖人工确认但没有人工证据，只能降级。

如果没有本轮新的有效证据，不能给 `pass`。

## 9. 输出约束

最终必须明确：

- 结论是 `pass`、`need-info` 还是 `blocked`
- 差异归类是什么
- 哪些点已确认一致
- 哪些点不一致
- 哪些风险未覆盖
- 是否需要回到 spec/detail 文档更新
- 如果不一致，是否已经明确列出打回主 agent 的修改项
- 如果经过 `ddev-clean`，是否已明确标注 cleanup 是否改代码，以及改后是否完成重审
- c-pro 规范审查是否已完成，结论是什么，若 blocked 是否附修改项清单

## 10. `need-info` 与 `blocked` 分流

- 缺信息但补齐后还能继续验收：`need-info`
- 基线冲突、关键文档缺失、实现偏离设计/计划，或前提不成立，导致继续验收没有意义：`blocked`

不要把所有“不够确定”都打成 `need-info`。
