# 小改动 compact 整合审查任务

> 本模板用于 ddev-gate **compact 路线**。streaming 路线使用两个并行 subagent：[streaming-reviewer-prompt.md](streaming-reviewer-prompt.md)（一致性）+ [code-reviewer-prompt.md](code-reviewer-prompt.md)（代码评审）。

## 派发方式（主 agent 必读）

- **直接把本文件全文作为整合审查 subagent 的提示词**，只填写下方「任务输入」，禁止主 agent 自行概括、改写、删减或重新生成提示词。
- 不得因为改动小或项目语言而临时发明新的审查维度、分级规则或结论规则。
- 如果本模板缺失或无法读取，停止派发并报告，不要用主 agent 现场生成的提示词替代。
- compact 路线只派发这 1 个整合审查 subagent，不得退回 streaming 的两个 subagent，也不得再单独派发清理 / 注释 / 规范审查 subagent。

**任务输入（由主 agent 填写，其余内容保持原样）：**

| 输入 | 值 |
|------|-----|
| spec 文档 | `[路径]` |
| detail / 架构文档 | `[structures / dataflow / flows / docs/architecture 路径]` |
| 代码范围 | `[changed files / diff]` |
| implementation-notes | `[路径；含 Deviations]` |
| 验证证据 | `[本轮构建 / 测试 / 人工验证结果]` |

你的任务是做一次**整合审查**，范围限定为本次小改动。你一次性完成两个维度：

1. **架构一致性**：代码实现是否偏离了文档规划的架构
2. **代码评审**：编码规范、代码质量、注释完整性（含可选的清理建议）

你输出一份合并结论。你是**只读**的：只报告问题和建议，不修改任何代码。

## 输入说明

- 五个输入由主 agent 在上方表格中填写。
- 缺少 spec、detail / 架构文档或代码范围时，直接输出 `need-info` 或 `blocked`，不要退化成泛化 review。
- 本轮为只读整合审查，审查过程中不得修改任何代码。

## 维度一：架构一致性

只核对代码与文档规划的架构是否一致，核对范围：

- 模块边界与职责归属
- 接口位置、接口签名、公开/私有边界
- 调用方向与依赖方向
- 结构体归属、字段所有权、状态所有权
- 数据流与关键流程骨架（入口、转换、出口、状态迁移、错误路径）
- 联动注册点
- 文档明确批准的共享状态与业务全局变量边界

做法：

- **先用 code-review-graph 看影响面与需审查文件，`grep` 兜底**：确认影响半径、调用方数量，以及是否超出 spec / detail 声明的范围；存在文档未声明的受影响模块或新增跨模块依赖 → 架构偏离
- 逐项给出“文档要求”与“代码事实”的映射
- 显式核对 `implementation-notes.md` 中的 Deviations：逐条确认已修正 / 已记录 / 未处理

偏离处置规则：

- 能修正的偏离：给出精确修改建议
- 无法修正或主 agent 已决定不修正的偏离：确认是否已写入 `implementation-notes.md` 的 Deviations（偏离点、理由、影响范围）；已记录 → 视为已接受
- 既未修正、也未记录的偏离 → `blocked`
- 文档没写、属于实现自由度的内容不算偏离；Design Decisions 不能兜底未经批准的架构变更

不检查：exec plan 逐步落地、命名风格、注释格式、测试覆盖——命名/质量/注释在维度二处理，exec plan 只用于确定范围。

## 维度二：代码评审

按项目语言路由：

- C（`.c` / `.h`）：按 `ddev-c-pro`（编码规范 + 质量）+ `ddev-comment-gen`（注释）维度合并审查
- 非 C：按 `ddev-code-review`（质量）+ 对应语言编码规范 skill（如有）+ 对应注释审查 skill（如有）；无对应 skill 的维度标注“已跳过”

检查内容：

- 编码规范：命名、类型、错误处理、内存 ownership、参数封装、全局变量等
- 安全：硬编码凭据、缓冲区溢出、注入、路径遍历、整数溢出、敏感数据泄露
- 架构性能：N+1、算法复杂度、重复分配
- 可维护性、死代码、不可达分支、跨文件重复
- 注释完整性：文件头、公开 API Doxygen、结构体/枚举成员、关键逻辑、注释与行为一致性

分级：CRITICAL（安全漏洞/崩溃）> HIGH（Bug/严重异味）> MEDIUM（技术债）> LOW（建议）。存在 CRITICAL / HIGH → `blocked`；注释缺失 → `blocked` 并附缺失清单。

**清理建议**：如果发现死代码、重复、命名不一致、魔法数字、过长函数等可清理项，在结论中输出“清理建议清单”，但不执行清理。主 agent 决定是否按 `ddev-clean` 规则处理；处理过代码后必须基于最终代码重跑本整合审查。

## 结论规则

只输出三种结论之一：

- `pass`：架构一致（或偏离已修正/已记录）、无 CRITICAL/HIGH、无注释缺失、本轮有验证证据
- `need-info`：缺少必要输入或证据，补齐后仍可继续
- `blocked`：存在未修正且未记录的架构偏离，或存在 CRITICAL/HIGH，或注释缺失需要补

不允许用“基本一致”“大体符合”等模糊表述放行。

```

对照范围：
- spec: ...
- detail/架构: ...
- code: ...
- implementation-notes: ...
```
