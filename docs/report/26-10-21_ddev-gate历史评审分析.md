# ddev-gate 历史执行分析（26-08 ~ 26-10）

> 目的：为 ddev-gate 技能优化提供数据依据。基于本机全部历史会话记录（DSH 会话存档）离线挖掘。
> 数据来自 `~/.dsh/sessions`（1447 个压缩会话文件，约 1.3GB），全量解压扫描，无抽样。

## 1. 口径与方法

| 项 | 说明 |
|---|---|
| 采集范围 | 2026-08-27 ~ 2026-10-21 全部会话（含 main 与 subagent） |
| gate 任务识别 | 主会话中出现「代码评审 / 一致性审查」类子代理派发记录 |
| 评审报告识别 | 上述主会话下挂的 `origin=subagent` 会话，取最后一条 assistant 正文 |
| 缺陷分类 | 优先解析报告内 markdown 表格/清单行；自由文本仅做关键词覆盖统计（标注为"提及"） |

**局限（先说清）**：
1. 报告结论格式不统一，约 21%（100/466）无常规"结论："行，通过率只能给区间。
2. 表格列序在不同版本提示词下不一致，分类按"问题描述单元格"与关键词混合判定，量级可信、个位数不可较真。
3. 用户主观评价只有 136 条直接纠错线索，无法做严格因果归因。

## 3. 流程各环节的实际价值排序

按"是否真正拦住问题 / 是否推动代码变化 / 是否可被替代"三项判断：

### 高价值（建议加强）

| 环节 | 证据 | 判断 |
|---|---|---|
| **影响面核对（实际改动 vs spec/detail 声明范围）** | 62 份报告明确以"影响面超出声明范围"立案；多份 blocked 的直接理由就是越界文件 | 最便宜、最硬的拦截，漏一次成本极高 |
| **spec ↔ 实现口径对照** | 155 份报告含"架构偏离清单"；blocked 条目中"spec 表述互相矛盾需定稿唯一口径"类占首位 | gate 的真正主业，且经常发现的是"文档自己打架"，只有独立第三方视角能发现 |
| **最终代码逐项复核（上轮修复是否真落地）** | 大量报告以 grep/read/逐行比对复核上一轮 HIGH 项，能抓出"声明已修复实际未落地"（如"声明 59 处已统一，实测仍余 14 处"） | 唯一防"假修复"的机制，不可省 |
| **注册点/枚举/事件表/配置表齐备性** | 42% 报告提及；漏注册属硬缺陷 | 该做成**机械清单**，不该靠模型逐轮回忆 |
| **接口/依赖方向/状态归属** | 一致性审查的主要结论区，pass 率相对高（约 6-7 成） | 收敛快、争论少，投入产出比最高 |

### 中价值（建议保留但压缩）

| 环节 | 证据 | 判断 |
|---|---|---|
| 死代码/零引用/未使用符号 | 34 条清理项、37% 报告提及 | 真实但低危，可脚本化 |
| 魔术数字/硬编码 | 22-31 条清理项 | 阈值型问题，脚本可查 |
| 测试/基线证据核对 | 115 份报告提及"验证证据"、128 份引用 `git status` | 有价值，但 reviewer 普遍无法复跑（见 4.3），多数只能"采信主 agent 声明" |
| 文档落盘/实施记录 | 84 份报告涉及文档口径 | 有价值，但与 spec 一致性重叠，可合并 |

### 低价值 / 高噪声（建议降权或脚本化）

| 环节 | 证据 | 判断 |
|---|---|---|
| **注释维度** | 清理清单中注释类约 **130 条**，远超死代码 34、魔术数字 31、过长函数 15；单是"术语/阶段标注泄漏"就出现在 **125/466（27%）** 的报告里 | 产出量最大、价值密度最低，是轮次膨胀主因之一 |
| 过长函数/拆分建议 | 15-53 份报告 | 反复"记录"但不修，纯占篇幅 |
| 存量坏味道 | 140 份报告出现"存量/非本轮/建议不改" | 与门禁目标无关，应默认排除 |

## 4. 高频错误榜

### 4.1 产品缺陷类（评审反复发现的）

| 排名 | 问题 | 报告覆盖 | 典型形态 |
|---|---|---|---|
| 1 | **注释类问题（合计）** | 约 62%（覆盖面最广） | 术语泄漏 125 / 冗余注释 53 / 英文注释 52 / 缺 `@file``@brief` 50 |
| 2 | 死代码、零引用符号 | 34-37% | 只在定义处命中、`nm` 无符号 |
| 3 | spec/文档口径矛盾 | 18-24% | 同一字段在 spec、detail、注释三处三套说法 |
| 4 | 魔术数字/硬编码 | 18-25% | 裸数字、裸缓冲尺寸 |
| 5 | 日志未走封装（裸 `printf`/`fprintf`） | 20-28% | 与 `prt_dbgi` 迁移半途而废 |
| 6 | 影响面超声明范围 | 13% | 顺手改了计划文件未列的文件 |
| 7 | 过长函数（>80 行） | 11% | 连续多轮"记录但不拆" |
| 8 | 定义处冗余 `extern` | 少量但顽固 | "声称统一、实测残留" |
| 9 | 注释与代码行为不一致 | 9% | "7 档" vs 6 条目 |

> 值得注意：第 1 名与第 6-9 名基本可不经模型判断，用脚本静态检查即可 100% 覆盖——现在却由 5KB 级报告逐条论述。

### 4.2 流程类错误（gate 自身故障，优化优先级更高）

| 排名 | 流程错误 | 频次 | 后果 |
|---|---|---|---|
| **1** | **轮次膨胀：任何改动都全量重跑 A+B** | 每任务中位 10 次派发，最大 50 次；自我报告轮次最高 **104 轮**（个别任务出现"终审 1~8""收口复审 1~2""复审 1~15"） | 成本线性放大；同一任务反复 10+ 轮很常见 |
| **2** | **"已记录"兜底被滥用** | 208 份报告出现"已记录/记录兜底"；140 份出现"存量/非本轮" | 问题合法不修 → 下一轮再报，形成长期空转 |
| 3 | 结论不可机读 | 100/466（21%）无规范"结论："行；格式有 `pass`、`**pass**`、`pass-with-findings`、`需要修改` 等至少 6 种 | 主 agent 判定依赖人肉解读 |
| 4 | 误报 | 36 份报告、**104 次**出现"误报" | 需主 agent 二次甄别，白耗轮次 |
| 5 | 只读 reviewer 无法复跑验证 | 26 份明确写"无法复跑/环境禁止 shell"，99 份写"未重跑" | 只能静态推理 + 采信主 agent 声明，易漏真问题 |
| 6 | 父会话中断 | 29 次（5.9%），均为 `aborted by parent` | 整轮评审白跑 |
| 7 | **reviewer 误加载 ddev-gate 本体** | 25/495（5%）子代理 skill 调用含 `ddev-gate` | 违反"提示词裁切"硬规则，存在自派发/自放行风险（本样本未发生，但属潜在失效） |
| 8 | 复审不收敛 | B 代码评审 pass 率约 **37%**，58% 的报告带 HIGH；A 一致性 pass 率约 6-7 成 | 瓶颈在 B，且每轮修完又出新 HIGH |

**A/B 收敛差异（关键）**

| 维度 | A 一致性审查 | B 代码评审 |
|---|---|---|
| 报告数 | 152 | 148 |
| pass 占比 | ≈65-70% | ≈37% |
| 带 HIGH 的比例 | — | **58%** |
| 平均每条报告的分级计数 | — | HIGH 1.27 / MEDIUM 5.06 / LOW 5.13 |

即：**一致性能收敛，代码评审不收敂**——每轮都稳定产出 1 个 HIGH + 10 个中低级项，而规则要求"修 HIGH → 重跑双审"，于是 A 被陪着反复跑。

## 5. 根因：三条互相放大的回路

1. **修复-重跑回路**：SKILL.md「只要本轮发生过任何代码修改，就必须基于最终代码重新并行派发 A+B」+ B 每轮必出新 HIGH → 轮次无上限。
2. **注释补全回路**：「MEDIUM/LOW 注释缺口同轮补齐、冗余注释同轮删除」→ 每轮都产生代码修改 → 必然触发 1 号回路。注释类又是最大产出项，两个回路互相喂料。
3. **记录兜底回路**：「无法修正的写入 Deviations」→ 下一轮 reviewer 又读到同一偏离 → 再次列出 → 主 agent 再次记录。208 份报告出现"已记录"即为证据。

## 6. 优化建议（按优先级）

### P0 — 直接砍轮次（预期收益最大）

1. **A/B 独立收敛**：A（一致性）pass 后，仅当改动涉及"架构相关面"（模块边界/公共接口/依赖方向/状态归属）才重跑 A；纯注释/死代码/格式类改动不再重跑 A。
2. **B 增量复审**：复审只审「本轮 diff + 上轮未闭合项」，明确禁止重新全量扫描整仓（现在多份报告中出现 201 个文件级全量审查）。
3. **轮次预算**：每任务默认上限 3 轮（A/B 各算 1），超出即输出 `need-info` + 遗留清单，交用户裁决；禁止"终审 1~8"这类无限收口。
4. **MEDIUM/LOW 延后批量处理**：评审轮只拦 CRITICAL/HIGH；MEDIUM/LOW 只入清单，在最终轮一次性处理，避免"修 LOW → 触发重审 → 又出 LOW"。

### P1 — 降噪与机械化

5. **注释维度脚本化**：术语泄漏、缺 `@file`/`@brief`、英文注释、冗余注释、`#if 0` 残留等，全部改为确定性脚本检查（项目已有 `final_verify.py` 类工具），subagent 只解读脚本结果，不再逐条论述。仅此一项可压缩报告体量约 30-40%。
6. **默认排除项写死**：存量代码、非本轮改动行、`libs/` 第三方、测试产物目录——一律不报（现在 140 份报告仍在讨论存量）。
7. **记录兜底收紧**：写"记录"必须附三要素：不修理由 / 影响面 / 复核轮次；下一轮报告必须以"待闭环"区块追踪同一 ID，禁止重复展开叙述。
8. **误报治理**：报告强制增加"误报复盘"字段（本条是否误报/依据）；把被标误报 ≥2 次的规则改为白名单制。

### P2 — 输出与证据规范

9. **结论格式硬约束**：报告首行必须是单一 token：`pass` / `blocked` / `need-info`，其后才允许解释；附机读尾部 `SEV: C=.. H=.. M=.. L=..`。解决 21% 不可机读。
10. **证据分级**：明确"静态核对（grep/read）"与"可复跑验证（构建/仿真/真机）"两级，`pass` 只在后者存在时给；前者最多 `pass-static` 或 `need-info`。解决"无法复跑却采信声明"。
11. **dispatch 卫生**：reviewer 提示词首段加"禁止加载 ddev-gate / 禁止派发子代理"（现有规则在 SKILL 侧，未进入模板）；并用 `git status` + mtime 做回传校验（规则已有，需在报告中强制填写校验结果）。
12. **中断恢复**：父会话中断（5.9%）后，复用已完成的工具调用与部分结论，不整轮重派。
