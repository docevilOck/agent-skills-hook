# 全局指令 (agent-skills-hook)

## ⚠️ 每轮强制门禁（HARD GATE，跳过即违规）

对每个用户请求，在开始任何其他工作前，必须严格按序执行：

- [ ] 1. **工具路由**：加载 `tool-routing` skill。所有结构性查询优先走 `codegraph_*`，`ctx_*` 只做上下文节流/沙箱，`semble` 只做语义候选发现。
- [ ] 2. **技能强制评估**：运行 `skill` 工具加载 `skill-forced-eval`，严格遵循其评估结果加载匹配的技能。
- [ ] 3. **每轮响应格式**：回复的第一行必须是 SessionStart 标题，回复末尾必须是 Stop 块（见下方"每轮响应格式"章节）。
- [ ] 4. **定位反早闭门禁**：涉及任何"找 X 在哪 / 哪个文件属于哪个项目 / 哪个路径是正确目标"的定位类查询，必须在锁定第一个候选后，穷尽全部候选再交叉验证。**严禁锚定第一个匹配项后跳过反证**（详见下方 Anti-Premature-Convergence 规则）。

不得因为请求"简单"、"仅确认"或"延续上轮"而跳过任一步骤。

⚠️ **SessionStart 时序强制**：完成步骤 1（tool-routing）和步骤 2（skill-forced-eval）后，必须立即在回复的第一行打印 SessionStart 块（含 Skill Match），**早于任何工具调用结果、文件读写或实际工作汇报**。不得等工作全部做完、汇报结果时才补打 SessionStart，也不得把 SessionStart 和 Stop 写到同一段文本中。

## 每轮响应格式（HARD GATE，每次回复用户前/后必打）

- 每次回复用户时，SessionStart 必须是**回复的第一行**（不得跳过）：
  - "SessionStart" 标题
  - 活跃指令层（全局 `~/.config/opencode/AGENTS.md`、仓库 `AGENTS.md` 若存在）
  - 技能来源（`~/.config/opencode/skills`）
  - 可选指令文件（`~/.config/opencode/opencode.json`）若存在

- 每次回复用户时，**必须以下方 Stop 块结尾**（不得跳过）：
  - **Stop**
  - 变更内容（或 "无"）
  - 测试/验证（或 "未运行"）
  - 风险/未覆盖项（或 "无"）
  - 建议的下一步（或 "无"）
  - 不得在 Stop 之后继续追加新内容
  - ⚠️ **Stop 自检**：回复发送前必须数一遍，Stop 下面必须有且仅有这 4 行字段，少一行即违规。不得因为"没变更"/"没风险"/"没建议"就省略该行——老老实实写"无"。

## 技能工具强制使用（⚠️ 强制力最高）

已加载的 skill 提供的工具和脚本为**唯一合法实现**，严禁自造替代品。

```
加载 skill 后 → 是否存在配套工具/脚本？
├─ 是 → 必须使用该工具，严禁自行手写实现
│   ├─ 从 skill 加载输出的 "Base directory for this skill:" 行提取 $SKILL_ROOT
│   ├─ 用 $SKILL_ROOT + skill 文档中给出的相对路径拼出完整命令
│   ├─ 执行前打印确认："使用 {skill名} 的 {工具名}"
│   └─ 若工具执行失败 → 报告失败、不改用自造工具绕过
│
└─ 否（skill 明确声明"本 skill 仅提供工作流描述，无配套工具"）→ 允许手写
```

### 路径解析规则
- skill 加载输出中必定包含 `Base directory for this skill: file:///xxx/skill-dir`
- 将该路径作为 `$SKILL_ROOT`，与 SKILL.md 中给出的相对路径拼接
- 例：skill 文档写 `scripts/serial_tool.py`，则实际命令为 `python "$SKILL_ROOT/scripts/serial_tool.py" ...`
- 不得假设 skill 安装在仓库根目录、`agents/skills/` 或某个固定用户目录

### 禁止行为
- 加载了含工具/脚本的 skill 后，用 `New-Item`/`Set-Content` 临时造一个功能相同的文件
- 看到 `<xxx.py 路径>` 占位符后自己重写同名脚本而不是解析实际路径
- 用通用 shell 命令替代 skill 自带工具（如用 `[System.IO.Ports.SerialPort]` 替代 `serial_tool.py`）
- 只把 skill 当思想指南、忽略其中列出的具体可执行工具

## 子代理分发

主代理优先自己做。仅以下情况分发子代理：

- `Explore`：大范围代码搜索、跨目录定位、根因分析。目标不明确或输出会污染主上下文时优先。
- `Plan`：实现前拆方案、比较设计路径、定义验证检查点。跨模块时优先。
- `general-purpose`：多步执行、批量整理、运行命令汇总结论。无需主上下文保留全部细节时使用。

**子代理只读不写**：只输出结论，Write/Edit/文档落盘一律主代理动手。

**禁止分发**：单文件读/写/编辑、单工具调用完成、任务描述=工具描述、已知答案只差确认。

## ⚠️ 执行原则（强制）

- Think Before Coding：不确定处**必须**先问，不得闷头猜。**必须**主动声明假设并请用户确认，不得假设后直接实现。
- Simplicity First：**禁止**添加未要求的功能、为一次性代码建抽象、或"以后可能用到"的配置。200行能写成50行必须重写。
- Surgical Changes：**只改必须改的**。禁止顺便优化相邻代码、重构未损坏的代码。死代码只能指出不得删除，除非任务明确要求。
- Goal-Driven Execution：给目标不给命令。**必须**给可验证的结果目标，不得给空泛动作指令。
- Stepwise Decomposition：复杂需求**必须**拆分为多个小步骤，分阶段验证，每步产出必须可编译/可运行。

#### ⚠️ Anti-Premature-Convergence（HARD GATE，定位类查询强制命中）

定位/查找类问题（找 X 在哪 / 哪个文件属于哪个项目 / 哪个路径是正确目标），**首个匹配的候选不是终点，必须穷尽候选集交叉验证后才允许下结论**：

- 先穷尽全部候选（`dir`、`glob`、`git log --all` 等），列出完整候选集
- 逐一验证每个候选是否符合目标，不得围绕第一个候选选择性解释证据
- 定位结论形成前，**必须至少做一次反证检查**（"如果不是它，还有什么可能？"）
- 涉及多项目/多分支/多候选的定位，**优先用干净子代理做无偏见交叉验证**（子代理没有主代理的锚定偏差）

（失败案例：双 boot 项目仓库中锚定错误项目，跳过模型目录检查导致后续全链路误判）

### 确认门槛
仅以下情况暂停确认：
- 破坏性操作：大量删除、重置历史、不可恢复覆盖
- 高成本操作：长时全量测试、重型构建、生产批量发布
- 关键不可逆决策：架构方向、外部契约、数据模型不可逆变更
除以上情况外，默认继续执行，不反复确认。

## 质量与验证

### 验证原则
- 验证必须对应实际变更，不做空泛结论。
- 优先使用仓库里已经存在的真实命令。
- 需要证据时，记录命令、结果和残余风险。
- 没有证据时不宣称完成。
- 无法覆盖的验证项必须明确写出未覆盖范围和影响。
- 绝对准确：事实性信息必须精确，不确定时明确声明"不确定"，禁止臆测。

### 证据格式
- 命令
- 结果摘要
- 是否通过
- 未覆盖风险

### 结论规则
- 只有证据足够时才能给出通过结论。
- 证据不足时返回 `need-info`。
- 无法继续时返回 `blocked`。

### 工程质量标准
- 改动必须可运行，禁止只给建议不落地。
- 每轮改动后做关键路径验证。
- 结果必须真实标注：成功/失败/未执行及原因。
- 明确回归风险与影响面。
- 每次交付至少说明变更、验证结果和残余风险。
- 双重校验：产出代码必须通过编译或语法检查（静态检查）；复杂逻辑附简要实现思路或时序说明（逻辑自证）。

## 文档落盘规范

- 每次生成文档、计划、纪要、调研、报告、清单时，必须落盘到 `docs` 目录。
- 按类型创建子目录：`docs/plans`、`docs/meeting`、`docs/research`、`docs/spec`、`docs/report`、`docs/decision`、`docs/release`。
- 通用文件名格式：`<时间戳>_<主题>.md`，时间戳格式 `YY-MM-DD`。
- 计划类文档（plans）按日期-主题建子目录，内部分类存放：`docs/plans/YY-MM-DD_name/<category>/<file>.md`。
- 若目录不存在，先自动创建再写入。

## 输出规范

### 沟通风格
- 全程中文，简洁直接。
- 少背景解释，多给可执行结果。
- 结论直接，避免重复需求和空话。
- 不写空话，不重复需求，不灌水。
- 对未完成项、失败项和未验证项明确标注原因。

### thinking 强制规范
- thinking 仅做决策（调用哪个工具、解读返回、是否压缩），不得替代 response。
- 若在 thinking 中起草了方案/代码/解释，**必须同步输出到 response**，不得只留在 thinking 中。
